## 1. 目标、范围和确认记录

正常出场消息的唯一计费链路如下；实时消息、补拉消息及管理员确认的修复最终都复用同一服务、核心、SQLite事务和发送任务：

```text
OneBot v11 群消息
  → 现有 hyw_assist 群开关
  → 本群 auto_cost 开关及真实发送者 QQ 校验，解析绑定的门店配置
  → 解析出场消息，以消息时间和展示时长重建完整访问
  → 门店账本内按卡号跨段去重及检查已出账冲突，读取当前计费段的完整历史
  → 后台已配置时优先查询最新折扣，失败用该店该会员已存折扣，无缓存则原价
  → 为本次访问记录实际采用的四个价格金额，历史访问保留各自金额
  → 调用现有 hyw_cost.calculate_bill
  → 原子保存访问和本次应收
  → 引用本群对应出场消息，回复卡号、昵称、本次时长、本次应付
```

本期只计算并播报应收，接入用户提供的只读会员模块，并包含断线/重启历史补拉、管理员发起的第一版单卡修复及单卡重新起算保底。后台已配置时按“最新成功折扣 → 同店同卡上次成功保存的折扣 → 无缓存则原价”选价；后台明确关闭用原价。折扣从本次起生效，保留当前段原计时及已计费金额，不回改旧账或退款。部署固定为现有单机、单机器人进程及SQLite，不新增中间件、独立服务或其他存储执行路径。不执行扣费、收款、退款、订单或会员资料修改，不新增进场解析、普通会员计费查询或自动历史更正。管理功能限第9.3～9.5节；修复不提交任何旧账金额变化，管理员另可预览并确认封存旧段、放弃旧段累计后恢复该卡新业务。摄像头配置、人数服务及其忙碌锁保持现状。

以下Q1～Q22为用户已确认的业务约束，与历史方案的问题编号无关。Q13～Q18取代早先“一次故障就换账本、会员失败暂停、会员价格固定”的讨论；Q19～Q22记录最终接口及恢复范围，Q22增加单卡保底，并限定其他累计、顺序及暂停规则作用于当前计费段。字段、命令和事务等具体工程约束见后文，不冒称用户逐项指定：

| Q16 | 保持单机部署，不增加任何其他中间件或服务；沿用现有机器人进程、NapCat及本地SQLite，在既有插件内实现队列和恢复逻辑 |
| Q17 | 后台已配置时，每次有效新访问先查询最新会员折扣；获取失败时使用该店该会员此前成功保存的折扣；没有有效历史折扣的会员按无折扣处理。查询失败及折扣来源切换本身不暂停计费；后台明确关闭仍按原价 |
| Q18 | 新折扣从本次访问起生效，保留此前计时进度和已计费金额，后者继续占用对应时段的新封顶；如已计费20元、新封顶62.4元，后续最多再计42.4元。已超过新封顶时该时段后续为0元，不自动退款、不重置该会员免费或封顶进度 |
| Q19 | 核心仍保持无状态，每次只传一份当前有效BillingConfig；历史访问仅携带当时小时价及三个封顶的四个金额，不各自创建完整BillingConfig |

| Q21 | 单卡修复纳入本期，由管理员查看问题、提出修复、预览并确认后原子提交，再恢复该卡；第一版只处理未结算问题来源，允许确认误报、人工关联重复、按证据修正输入。任何已有账单金额变化都只报告差异、不提交；不清空整店账本 |
| Q22 | 单卡重新起算纳入本期保底：管理员预览并确认后，保留旧账、问题及发送记录，封存该卡旧段并从新起点计费，不要求补齐或对平旧历史。免费、计时及封顶进度重置，折扣缓存保留；门店ledger_id、规则及其他卡不变。仅新增一个重开子命令，复用确认/审计，无JSON修复清单、后台查询、历史补拉或重算前置；重开不自动触发。仍保留跨段去重及已出账冲突检查，不能解除整店未知卡号/恢复阻断或绕过存储和程序故障 |

已检查的主要依据：

- [插件入口](../../../nonebot/src/plugins/hyw_assist/__init__.py)、[摄像头配置](../../../nonebot/src/plugins/hyw_assist/config.py)：目前已注册业务仍只有人数统计。
- [群配置解析](../../../nonebot/src/infrastructure_plugins/group_config/config.py)、[启动快照](../../../nonebot/src/infrastructure_plugins/group_config/service.py)、[分发前置校验](../../../nonebot/src/infrastructure_plugins/group_config/__init__.py)：目前各群只允许 `enabled`，且快照仅保存开关，门店配置的正式读取尚待实现。
- [适配桥](../../../nonebot/src/infrastructure_plugins/_adapter/onebot11.py)：已有群及发送者识别方法；本期引用及时间字段直接使用 OneBot 事件能力，不扩建通用适配接口。
- [核心说明](../../../nonebot/src/plugins/hyw_assist/hyw_cost/README.md)、[公共模型](../../../nonebot/src/plugins/hyw_assist/hyw_cost/models.py)、[输入校验](../../../nonebot/src/plugins/hyw_assist/hyw_cost/validation.py)、[重放计算](../../../nonebot/src/plugins/hyw_assist/hyw_cost/calculation.py)：核心当前只支持一份固定配置重放，金额字段必须大于0；须在同一核心中扩展0价格和逐访问价格快照，延续原计时、步长和时段归属语义，不在插件另算账单。
- [会员模块](../../../nonebot/src/plugins/hyw_assist/hyw_membership.py)：已改为接收门店快照，保留真实后台登录、分页、详情核对及折扣读取；不自行读配置文件或环境变量，不注册群消息处理器。

以下为实施目标契约；核心每次只接收一份完整的、已应用本次折扣的 `BillingConfig`。历史访问仅附带过去实际采用的金额快照，固定时段规则不重复传入。现有 `Visit` 尚无 `applied_price`，现有核心也尚不能按历史金额重放；主体实施时同步更新核心、全部调用方、核心说明及测试，不保留另一条旧固定价执行路径：

| 项目 | 必须遵守的约束 |
|---|---|
| 入口 | 相对导入现有 `hyw_cost`，统一调用 `calculate_bill(visits, billing_config)`；只传一份本次有效 `BillingConfig`，同时提供本账本固定的时段、免费阈值和步长。核心按历史金额快照重放前史，处理本次时使用该配置的单价和封顶 |
| 访问集合 | 内置 `list[Visit]` 或 `tuple[Visit, ...]`；同一门店账本、同一卡号，从当前计费段开始至目标访问的全部有效原始访问。未重开时该段自账本起点开始；段筛选在业务层完成，不给核心增加段参数 |
| 已出场记录 | 扩展为 `Visit(entered_at=..., exited_at=..., applied_price=...)`。新增必填字段：历史访问为不可变 `AppliedPrice`，本次访问显式为 `None`；本次价格唯一来自外层配置。均为已闭合访问，不传 `as_of`，不创建虚构进场消息或未出场访问 |
| 本次定义 | 核心按入场时间排序后选择最晚一条。插件须先拒绝新收到的晚到历史，不能让核心把另一条访问当作本次 |
| 时间 | 确切的 `datetime`，时区为标准库 `datetime.timezone`；统一固定 UTC+08:00、`fold=0`，不用无时区时间或 `ZoneInfo` |
| 合法区间 | 出场严格晚于入场；不重叠、不重复；相邻访问的前次出场等于后次入场合法 |
| 日期域 | 转换为北京时间后位于 `0002-01-01` 至 `9998-12-31`，越界作为输入错误 |
| 本次金额 | 直接取 `BillResult.current_payable_fen`，是本次访问新增应收；不再次减去上次金额，不读取第三行金额或付款状态 |
| 本次时长 | 取 `BillResult.current_presence_seconds`，不能使用统计日累计时长代替本次时长 |
| 历史重放 | 每次传当前计费段全部历史和本次配置；历史访问分别携带当时已保存的四个金额，不能把本次新折扣应用于过去访问。付款、跨午夜、跨日、封顶及已播报均不是截断历史的理由；只有Q22经确认建立的新段改变重放范围，旧历史保留 |
| 历史金额 | `AppliedPrice`仅含 `hourly_rate_fen`、`day_cap_fen`、`night_cap_fen`、`early_bird_cap_fen`；金额为严格整数 `0..2**63-1`，拒绝bool/float/数字字符串，早鸟关闭时最后一项为None。不含时段、免费阈值、步长或另一份BillingConfig |
| 价格约束 | 外层配置的时段边界、早鸟开关、免费阈值及步长须与账本基础快照一致，由插件在读取账本时核对；核心校验历史金额及早鸟开关对应关系。排序后仅本次访问可有 `applied_price=None`，其他访问缺少历史金额必须拒绝，不能用当前价格补齐 |
| 核心异常 | `BillingConfigError`、`BillingInputError` 是业务校验异常；`TypeError`、`RuntimeError` 属于集成或内部错误，不伪装成免费结果 |

核心固定使用北京时间，日间和每个具体夜间分别封顶；没有整次访问或滚动 24 小时统一封顶。早鸟与基础时段、当日日间共享实际已计费预算，不预占整份30元额度。逐访问变价时保留原计时上下文及已触发计费节点，当前访问触发的新增费用采用当前价格；对应预算的剩余额度为 `max(0, 当前封顶 - 历史实际已计费金额)`，不把历史金额按新系数重算。插件层只选择折扣并转换有效配置，不另实现收费公式、套餐选择或封顶逻辑，也不在结果上再次乘折扣。

核心扩展仍只有一个Replay：按访问切换四个有效金额，不为历史构建配置对象。预算身份仍是时段种类及开始时刻，限额可以随访问变化，已用金额不得清零；允许历史已用金额大于后来降低的限额，替换当前不允许该情况的预算守卫。首小时/步长“已触发”与“实际收费/跨时段覆盖”分开记录，0元也不能使同一节点重复触发；原跨时段权益仍遵守现有实际收费语义。累计名义费用的整数精度及舍入余量保留，不因换价清零；固定正价的原21组及原核心完整契约继续回归。

历史缺少金额使用BillingInputError的 `MISSING_APPLIED_PRICE`，本次另带金额使用 `UNEXPECTED_APPLIED_PRICE`；金额类型/范围继续用 `INVALID_TYPE/OUT_OF_RANGE`，早鸟金额存在性不符用 `INCONSISTENT_EARLY_BIRD_PRICE`，field定位到原输入下标及具体字段。配置本身错误仍是BillingConfigError，不把历史输入错误混成免费结果。

现有 Docker 为 Python 3.12，本次只读核验环境为 Python 3.13.11。`pyproject.toml` 当前声明支持 Python 3.8，但核心使用的 dataclass 参数等已不支持 3.8；实施时将运行版本声明对齐现有部署要求 `>=3.12, <4.0`，验证 3.12 和 3.13，不增加旧 Python 兼容层。

## 3. 门店配置与群绑定设计

### 3.1 唯一入口与完整示例

唯一配置入口仍为 `GROUP_CONFIG_FILE`，默认 `nonebot/plugin_data/group_config.json`，路径解析及启动快照机制沿用现有实现。`hyw_assist.stores.<门店ID>` 保存门店计费配置，`hyw_assist.groups.<群键>.auto_cost` 保存该群的门店绑定、开关和消息来源。同一家门店由多个群引用，规则、凭据和账本阶段只维护一份。

一个群最多绑定一家门店，一家门店可以绑定多个群；群内指定的广播 QQ 必须只发送该绑定门店的出场播报。本期不根据昵称、时间或消息第三行猜测门店，也不支持同一群混播多店后自动分流。摄像头参数继续使用已有配置入口，不随此次门店计费配置迁移。

    "private_enabled": false,
    "stores": {
      "hyw-store-001": {
        "ledger_id": "2026-11-initial",

只要配置 `hyw_assist`，其 `default_enabled`、`private_enabled`、`stores`、`groups` 四项都必须显式填写。`stores={}`、`groups={}` 均允许；可以预先配置尚无群绑定的门店，但这些门店不启动账本。`hyw_assist` 整项未配置也仍合法，表示没有群自动计费配置。

所有现有 `hyw_assist.groups` 条目，包括关闭的群和 `qq:` 群，都在实施升级时补齐 `auto_cost`，且固定包含 `enabled`、`store_id`、`broadcast_qq`。关闭且未绑定时后两项为 `null`，无需创建虚拟门店或在群内复制规则；也可保留有效门店引用及来源 QQ 后关闭开关。

每个门店条目必须完整填写 `ledger_id`、`backend`、`billing`；`billing` 示例数值即用户要求的默认模板，程序不在缺项时静默补值。门店 ID 直接取 `stores` 的键，门店对象内不重复增加 `store_id`。

不保留缺少 `stores`、缺少群 `auto_cost`，或把 `ledger_id`、`backend`、`billing` 嵌入群 `auto_cost` 的旧结构作为兼容路径。其他插件保持原配置结构，禁止填写 `stores` 或 `auto_cost`。

### 3.2 字段与校验

| 门店字段 | 类型及约束 |
|---|---|
| `stores` | 必填对象，键为实际门店 ID，值为完整门店配置；允许空对象 |
| `stores` 的门店 ID 键 | 非空字符串，无首尾空白，区分大小写；作为门店唯一身份，不按名称、群号或整数转换猜测 |
| `ledger_id` | 必填非空字符串，无首尾空白，区分大小写；是门店内人工指定的账本阶段标识，不使用进程启动时间随机生成 |
| `backend` | 必填五字段对象，包含 `base_url`、`username`、`password`、`timeout_seconds`、`allow_http`；凭据三项全为 `null` 明确关闭会员查询，或三项全部填写后启用查询；不接受部分填写 |
| `backend.base_url` | 配置时为合法绝对 HTTP/HTTPS 后台目录 URL，不含内嵌用户名密码、查询参数、fragment 或空白；标准化为尾部一个 `/`。目录可用于限定门店，不能填成某个 PHP 文件地址。HTTP 须同时显式开启 `allow_http` |
| `backend.username/password` | 配置时非空；密码原样保留且使用 `SecretStr` 承载，不输出模型或配置原文，不保存到计费数据库 |
| `backend.timeout_seconds` | 必填有限正数，单位秒，拒绝布尔值及数字字符串；模板为15，作用于每次 HTTP 请求，不是整个分页查询的总时限 |
| `backend.allow_http` | 必填严格布尔值；模板为 `false`。沿用原模块的 HTTP 显式许可要求，HTTP 地址必须设置为 `true`，HTTPS 不要求此许可 |
| `billing` | 必填完整对象，字段与核心一一对应；不允许额外字段 |

| 群字段 | 类型及约束 |
|---|---|
| `groups.<群键>.enabled` | 沿用原有严格群开关，控制该群整个 `hyw_assist` 插件 |
| `auto_cost` | 必填对象，只允许下列三个字段，不保存门店规则、凭据或阶段标识 |
| `auto_cost.enabled` | 必填严格 JSON 布尔值，拒绝字符串、数字、`null` |
| `auto_cost.store_id` | 必填；开启时为与 `stores` 键完全相同的非空字符串，关闭时允许 `null`。只要不是 `null`，即使群或自动计费关闭，也必须引用已定义门店；不存在的引用阻止启动 |
| `auto_cost.broadcast_qq` | 必填；开启时为满足 `[1-9][0-9]*` 的实际发送者 QQ 号字符串，关闭时允许 `null`；非空时无论开关状态都须满足该格式。不按昵称、群名片或被引用消息作者匹配 |

开启自动计费的 `auto_cost` 只能出现在 `onebot11:` 群键下；`qq:` 群即使总群开关关闭，也不能配置 `auto_cost.enabled=true`。一个配置文件中可同时保留 QQ 官方适配器的其他群策略；OneBot 计费条目不会使 QQ 进程启用计费。自动计费不处理私聊、频道、频道私信、通知或机器人自身发送的消息。

实际执行须同时满足：插件已加载、现有群策略允许、本群有明确条目、`auto_cost.enabled=true`、绑定门店已定义、当前适配器为 OneBot v11、真实发送者等于 `broadcast_qq`。从 `stores[auto_cost.store_id]` 获取唯一的后台、规则和账本阶段。`default_enabled=true` 不会给未列出的群自动绑定门店。总群开关与自动计费开关互不替代；私聊开关不能启用自动计费。

`stores.<门店ID>.billing` 的具体约束：

| 配置字段 | JSON 表达及转换 | 默认模板 |
|---|---|---|
| `day_start` | 严格零填充的 `HH:MM`，00:00～23:59，转无时区 `datetime.time` | `12:00` |
| `night_start` | 同上，严格晚于 `day_start`；同时为日间结束及夜间开始 | `22:00` |
| `hourly_rate_fen` | 严格整数，`1..2**63-1`，单位分，不收元单位浮点数 | `2000` |
| `day_cap_fen` | 严格整数，`1..2**63-1`，单位分 | `7800` |
| `night_cap_fen` | 同上 | `7800` |
| `first_hour_free_seconds` | 严格整数，`0..3599` | `900` |
| `step_seconds` | 严格整数，`1..2**63-1`，不额外要求整除 3600 | `900` |
| `early_bird` | 显式 `null` 表示关闭；开启时完整包含下列三项 | 开启 |
| `early_bird.start/end` | 同日 `HH:MM`，`start < end`，不隐式跨午夜；允许与基础日夜时段重叠 | `08:00` / `12:00` |
| `early_bird.cap_fen` | 严格整数，`1..2**63-1`，单位分 | `3000` |

时段配置本期开放到分钟精度；首小时固定 3600 秒、计费时区固定 UTC+08:00，没有 `timezone`、`day_end`、单独夜间单价、整次统一封顶等字段。布尔值不能充当整数；拒绝浮点数及数字字符串。核心允许封顶低于小时单价，也允许早鸟跨基础日夜边界，不添加相反限制。

沿用标准 JSON、UTF-8 无 BOM、重复键拒绝、未知字段拒绝和错误位置脱敏规则。所有门店、群条目及非空门店引用都校验，包括未绑定门店、关闭群及当前未加载的业务插件；错误阻止启动，不忽略错误条目继续运行。配置更改须重启生效。

### 3.3 启动快照、门店引用与变更

- 在 `group_config` 内增加 `hyw_assist` 专属的严格类型，复用通用群开关结构；其他插件保持原校验。不把 `extra="forbid"` 改为宽松字典。
- 同一次读取中解析门店表、群绑定和群开关，快照保留递归不可变的门店配置及绑定；门店条目以只读 Mapping 提供给会员模块，密码值保持 `SecretStr`。提供按群键解析的单一接口，例如 `get_auto_cost(group_key)`。无群条目或 `store_id=null` 时返回 `None`；已绑定时返回该群的自动计费开关、来源 QQ 和所引用的门店配置，后者复用快照中的同一份对象，不为每群复制。业务插件不再次打开 JSON，也不自行拼接另一套门店查找流程。
- 配置模型属于基础配置层，不从基础插件导入 `hyw_assist.__init__`，避免触发摄像头初始化或产生循环依赖。插件只做JSON类型到核心模型的显式转换。后台目录URL不能是PHP文件的约束须补齐到现有校验及测试中；当前会员构造器仅校验协议、凭据、端口等，不能把既有代码状态冒称已满足全部目标规则。
- 同店多群只引用同一个 `stores` 条目，自然共享 `ledger_id`、`billing` 和 `backend`；无需再维护跨群重复参数的一致性比较。各群的开关及 `broadcast_qq` 可以不同。
- 启动时校验所有非空门店引用存在；重命名或删除门店时须同步更新全部引用，包括关闭群。禁止在引用失效时按群新建门店、选第一个门店或忽略该群。
- 只对本进程至少有一个实际启用群的门店初始化账本；多个群只初始化一次。单纯在 `stores` 中预配门店、全部绑定关闭或当前运行于 QQ 官方适配器时，不因这些条目创建或切换账本。
- 对实际启用门店，将规范化的 `billing` 序列化并计算规则摘要。已有 `(store_id, ledger_id)` 的摘要不一致时启动失败，提示修改该门店的 `ledger_id`；不以新配置重放旧账本。更改一店规则只影响该店，其他门店仍使用各自独立配置。
- 群改绑门店不迁移已记录历史、既有应收或待发任务。待处理记录持久化接收时的门店和阶段；恢复前须确认该群仍绑定原门店、原阶段，改绑后的旧任务暂停，不能用新门店参数重新处理。改绑前先核对旧广播和积压，来源必须与新绑定门店一致。
- 关闭自动计费仍校验所填字段，但不初始化相应账本或发起任何网络请求。配置解析和客户端构造也不登录；只在处理有效新访问时查询已配置后台。人数统计仍遵守其原有初始化配置要求，本期不做独立加载重构。

## 4. 出场消息解析与时间重建

### 4.1 输入边界

仅从已授权发送者的 OneBot 群消息中识别候选：首个正文行以 `【` 开头且以 `出场了！` 结尾。其他消息静默跳过。候选消息解析失败才生成核对提示，避免对该 QQ 的所有聊天逐条报错。

正文统一将CRLF转LF，移除正文首尾空行及各行首尾的空格/Tab；不合并中间空行或跨消息拼接。实时来源明确读取OneBot事件的 `original_message`（[已用适配器版本模型](https://raw.githubusercontent.com/nonebot/adapter-onebot/v2.4.6/nonebot/adapters/onebot/v11/event.py)），不能用已移除引用/@的处理后正文规避检查；候选中的图片、转发、引用或@均拒绝，也不提取其内部文字。历史响应的message经同一个OneBot Message构造规范化成消息段，执行相同判断；始终使用原发送者及时间。

必须完整匹配两行或三行：

```text
【4637】piment 出场了！
在场时长:6小时22分钟
结算金额¥:98(学生卡)
```

| 部分 | 明确规则 |
|---|---|
| 首行卡号 | `【`、一个或多个 ASCII 数字、`】`；按字符串保存，保留前导零，不限制为四位，不转换成整数 |
| 首行昵称 | 去除卡号后的首尾水平空白，保留内部空格及 Unicode 字符；非空、不得含控制字符；昵称与固定后缀 `出场了！` 之间至少一个空格或 Tab |
| 第二行前缀 | 固定为 `在场时长:`，冒号后允许水平空白；不擅自支持中文冒号、英文单位或其他模板 |
| 时长 | 非负 ASCII 整数组成的 `H小时M分钟`、`M分钟` 或 `H小时`。组合形式的分钟为 0～59；仅分钟形式可大于 59；总分钟必须大于 0 |
| 第三行 | 可以完全不存在；存在时须以 `结算金额¥:` 开头，其后文字不参与数值解析、卡类型判断或折扣判断 |
| 其他内容 | 额外行、正文中间空行、小数时长、负数、秒数、缺昵称、缺卡号、非法组合分钟等均不接受 |

正则需使用完整匹配及 ASCII 数字范围，不使用会跨行吞掉正文的 `.*` 或把全角数字视为卡号的 `\d`。昵称始终作为普通文本构造回复，不解析成 CQ 码。

### 4.2 权威时间来源和精度

1. 出场时间取 OneBot 事件 `time` 的 Unix 秒值，使用固定时区明确转换为北京时间；不是机器人处理时间、数据库写入时间或开发机日期。
2. `duration_seconds = total_minutes * 60`，入场时间为 `exited_at - timedelta(seconds=duration_seconds)`。保留事件时间本身的秒数，不把整条时间取整到整分钟。
3. 入出场区间采用 `[entered_at, exited_at)`；不插入离店间隙、不拆成伪造访问，也不按时段边界提前切记录，交由核心处理。
4. 消息中的整数分钟是本期认可的事实精度。即使广播来源隐藏了秒数，也不补造 `:59`、平均误差或宽限时长。
5. 缺失、非整数或越界事件时间，非法总时长，时间相减溢出，以及总时长 0，均不构造合法访问或返回金额 0。

例如出场消息时间为 `2026-11-02 18:22:37+08:00`，展示 `6小时22分钟`，则重建入场为 `12:00:37+08:00`，在场精确为 22920 秒。

## 5. 账本、身份和完整历史

### 5.1 账本阶段

- 账本身份为 `(store_id, ledger_id)`；用户身份为 `(store_id, ledger_id, card_number)`。昵称不是主键，群号及广播 QQ 也不是会员身份。
- 每张卡统一关联 `card_segments`，首次归类到该卡时建立第1段，起点采用账本创建时刻；历史重放范围为该卡的当前段。只在管理员确认Q22重开时新建下一段，不为正常卡和重开卡分设两条计费路径。
- `store_id` 来自群绑定所引用的 `stores` 键，`ledger_id` 来自该门店唯一配置；同店多群不创建独立账本。群增删或改绑只改变消息路由，不迁移历史或重新归属既有账单。
- 账本第一次被有效开启时，在本地数据库持久化创建时刻和规则快照；相同阶段重启复用，不能每天、每次启动或每次返场重建。
- 只接纳出场消息时间不早于该账本创建时刻的访问。首条访问的入场可以早于创建时刻，保存完整区间。启用前已经出场的消息不补导，也不以接收时刻伪装成新出场。
- 不同门店互不累计；同门店同卡号在当前段的全部有效访问跨群共享进度和封顶。卡号 `04637` 与 `4637` 是不同身份。
- 改变门店基础价格/时段规则或整店历史无法补齐时，配置新的、从未使用过的 `ledger_id`；可定位单卡的历史问题可按第9.5节只重开该卡。会员折扣或折扣来源改变则按Q17/Q18在原段继续。旧账本阶段关闭并保留；不得切回已关闭阶段继续追加。一个门店同时只有一个活动阶段，一张卡在该账本内同时只有一个活动计费段。
- 新阶段不继承旧阶段的封顶、免费进度、付款或历史；这是明确的新账本业务边界，不宣称等价于会员真实终身历史。

临时关闭、断线及停机可能漏掉广播，按第9.3节先补拉并确认原事件完整，再按序恢复；缺口尚未核清时先暂停该店新结算。来源仅在内存、尚未落库时退出也适用此规则。恢复完整原事件后沿用原账本；单卡明确放弃旧段累计按Q22恢复，整店缺口无法补齐按Q8重开，均保留旧问题且不要求先把旧账对平。补拉不保证找回平台未保存或已不可查的内容；本期也不允许凭空手工编造访问或把重新发送正文的新消息当作原事件。

### 5.2 历史读取与去重顺序

每次处理在同一数据库事务的一致视图中完成以下判定：

1. 先检查传输消息键 `(adapter, bot_self_id, group_key, message_id)`；重复投递直接使用已有状态，不生成新访问或新发送任务。
2. 以 `(store_id, ledger_id, card_number, entered_at, exited_at)` 跨全部计费段检查业务重复，唯一键不加入段ID。完全相同的访问使用已保存结果，不再次调用核心累计；当前段同一来源群已有任务时不追加，封存段不再创建自动回复。
3. 对能确定卡号及原出场时间的新来源，按计费段时间界线归属；落入封存段则只保存原归属及待核对状态，不新增账单、后台查询或当前段阻断。已存来源优先复用其原段，不能随重开迁移；无法确定原时间或卡号时不能假定属于旧段，按正常核对范围处理。
4. 当前段的新记录检查门店阻断、同卡当前段未解决问题及较早未完成来源。仍在处理或等待重试的较早来源先完成，不因HTTP返回顺序把它判成迟到；当前段相对已结算历史真正迟到、部分重叠、包含、同入场不同出场等均拒绝。另检查该卡跨段全部有效已出账访问，新访问与其重叠仍拒绝，不因重开放宽精确去重及冲突规则。
5. 新记录必须在该会员当前段现有访问之后；前次出场等于本次入场允许。同时间重复在第2步处理，不错误判定为迟到。
6. 读取该会员当前段内截至本次的全部有效原始访问，再追加本次访问，构造核心模型。段筛选不删除旧历史；不开启核心的“安全后缀”优化，不按今天、午夜或付款状态截断段内历史。

跨群镜像的消息时间若相差几秒，会导致重建区间不同；严格按 Q7 提示冲突，不使用容差、昵称相似度或相同展示时长推定同一访问。跨群的精确重复分别引用各群首次收到的对应消息，每群最多一次；昵称采用该条来源消息解析的显示值。

历史候选确定无效时不写入有效 `Visit`。当前段问题使该卡号进入历史待核对；候选无法定位合法卡号时，该门店阶段进入历史待核对。封存段已知归属的问题保留核对但不计入当前段阻断。临时网络或存储错误按第6.5节处理，不直接标记成历史损坏。卡号级问题不影响其他卡号或门店；普通非候选、已知重复、明确早于账本起点的旧消息，以及已保存账单发送失败不触发历史阻断。

历史待核对问题使用第9.4节的当前段修复流程，或第9.5节的单卡重开保底；普通重启不自动清除问题。修复仅处理当前段未结算来源，不变更原始来源、有效访问及旧账；发现旧账差额时修复不提交，管理员另可选择封存旧段继续新业务。重开不修正旧差额、不提供调账或退款，也不解除门店级阻断。存储/程序故障与会员查询异常仍分别按第6.5节和Q17处理。

### 5.3 同一卡号的队列与恢复顺序

- 服务对 `(store_id, ledger_id, card_number)` 使用同一串行队列，覆盖查询、结算、修复和重开；队列键不加入段ID，防止新旧段并行提交。不同卡号不因一张卡的后台查询而排队。SQLite事务与唯一键仍负责最终一致性。
- 已接收的候选先保存和解析归类，再按入场、出场时间及接收顺序选择待处理记录。恢复时先归类已有积压，再放行相关实时结算；无法确定卡号的未完成候选先在门店范围挡住可能受影响的新结算。
- 最终写事务除有效历史外，还须核对准备时的段仍活动及该段较早未完成来源；段已切换时旧计算不得提交，按原来源归属保留。若查询期间出现本段更早候选，则退回同一队列让其先处理。本段已结算后才到的更早历史仍按迟到处理，已封存段来源按第5.2节归档。
- 当前段较早记录处于有限重试、可恢复暂停或历史待核对时，后续记录保留原输入并等待；管理员确认封存后旧段不再参与此等待判断。尚能写库时仍保存后续来源；来源落库失败时按第6.5节在门店范围处理。
- 固定验收：同卡两次访问 `12:00–12:10`、`13:00–13:10` 均已收到，即使第一次会员查询更慢，第二次也必须带上第一次历史并应收20元，不能先报0元再把第一次当迟到。

## 6. 编排、持久化和并发

### 6.1 单一模块边界

在现有插件内扩展，职责划分如下；复用已提供并适配的会员模块，不新建平行后台客户端或第二个计费服务：

| 文件或模块 | 职责 |
|---|---|
| `infrastructure_plugins/group_config/hyw_config.py` | `stores` 门店配置、群 `auto_cost` 绑定及计费 JSON 的严格类型、字段和引用校验；由既有配置读取流程调用 |
| `infrastructure_plugins/group_config/config.py`、`service.py` | 按插件名选择对应配置模型，保留门店及群绑定的不可变快照，按群解析唯一门店配置；继续维持唯一群开关判定路径 |
| `plugins/hyw_assist/__init__.py` | 注册自动计费消息 matcher，接入启动、机器人连接及关闭生命周期；调用下列服务 |
| `plugins/hyw_assist/auto_cost/message.py` | 纯文本解析、规范化事件数据、回复文本格式化；不读数据库或请求网络 |
| `plugins/hyw_assist/auto_cost/repository.py` | SQLite初始化、事务、来源、账本、单卡计费段、历史、群恢复进度、修复/重开审计及发送状态 |
| `plugins/hyw_assist/auto_cost/service.py` | 唯一业务服务；实时/补拉来源、当前段顺序结算、恢复及修复/重开预览确认，构造同一核心模型及任务；重开只切换存储中的段，不增加收费算法或平行计费服务 |
| `plugins/hyw_assist/hyw_membership.py` | 接收单店后台配置，执行只读会员查询并返回两种精确折扣及原始会员信息；本轮已适配，不计算账单 |
| `plugins/hyw_assist/hyw_cost/` | 继续使用用户提供的原始核心，不改造成 NoneBot 插件、不引入网络和数据库依赖 |

`auto_cost` 子包初始化仅做必要导出，不注册第二套 matcher。现有 `config.py` 的摄像头参数仍走原有入口，不能顺带迁移到 JSON。

补拉由同一插件的启动、连接及管理命令触发，实时和历史记录统一规范化为同一来源输入；不伪造事件后重新分发给所有NoneBot业务matcher。第9.4～9.5节共用受限管理命令、群策略及SUPERUSER权限，重开只增加同一命令内的子操作。

自动计费 matcher 使用 `on_message`，优先级 5、`block=True`，只匹配来源及候选规则已经通过的出场播报。有效或异常候选均由本链路消费，避免昵称包含“音游几”等关键词时额外触发摄像头。普通消息不匹配此 matcher，关闭群由现有前置处理忽略，不阻断后续业务；均没有计费数据库及发送副作用。handler 统一通过服务发送，完成后返回，不另行回复。计费不占用人数统计的 `busy` 锁，不自行创建另一套群开关逻辑。

本期可以直接读取 OneBot 的 `time`、`message_id`，并构造 `MessageSegment.reply`；已经确认只支持 OneBot，不为 QQ 官方适配器增加空实现或用 @、文本前缀模拟引用。其他插件的适配行为不改变。

### 6.2 存储位置与数据

数据库固定为 `nonebot/plugin_data/hyw_assist/auto_cost.sqlite3`，相对现有 `PROJECT_ROOT` 解析，与工作目录及群配置文件自身位置无关。Docker 中对应 `/app/plugin_data/hyw_assist/auto_cost.sqlite3`，使用已有持久化卷，无新增路径配置。只在本进程确有可执行的自动计费群时创建目录、打开数据库。

上述是自动启动的资源边界；第9.4节显式管理员操作可打开此路径已经存在的数据库，不因关闭auto_cost自动创建数据库、账本或发起恢复。两种入口复用同一repository及事务实现。

使用标准库 `sqlite3`，通过参数化SQL操作；原始来源、折扣缓存、访问、结果及发送状态统一保存在这份数据库中，不增加中间件、独立服务或第二套存储执行路径。保存UTC整数微秒或等价无损时间值；账本启用界线单独按Unix整数秒记录，与OneBot事件精度一致。展示和核心输入再明确转换为固定UTC+08:00。

单价/封顶可用SQLite INTEGER；多日合计的本次应收可能超过单个64位整数，按规范十进制TEXT保存并严格还原为Python int，结果JSON仍保存整数。不能因配置金额合法就假定跨多日应收一定能放进SQLite INTEGER，不经float保存或比较金额。

必要数据结构：

| 数据 | 必须保存的内容与唯一约束 |
|---|---|
| `ledgers` | 内部账本ID、store_id、ledger_id、创建时间、活动/关闭状态、门店级待核对原因、规范化计费快照及摘要；唯一 `(store_id, ledger_id)`，每店最多一活动阶段。待核对仍占活动阶段，封存段单卡问题不构成门店阻断 |
| `card_segments` | 内部segment_id、账本/卡号、递增段号、起点/终点、active/sealed、创建或封存的repair_id及时间；唯一 `(ledger, card_number, segment_no)`，部分唯一约束保证每账本每卡最多一段active。第1段起点等于账本起点，下一段由Q22事务建立；封存不可重开 |
| `source_messages` | 内部source_id、传输消息唯一键、原群、机器人账号、发送者、原平台时间、接收顺序、live/history来源标志、接收时的门店/阶段、可确定卡号时的segment_id、正文及纯文本/消息段类型、规范化输入、状态/原因/重试阶段次数、脱敏错误、关联访问及repair_id。原始来源及已确定段不被修复或重开迁移；未知卡号暂不关联段。原文只保留一份，不保存附件二进制或配置凭据 |
| `member_discount_cache` | 同店同卡最近一次成功查询的两种精确折扣、查询时间及必要会员依据；唯一 `(store_id, card_number)`。跨群、普通重启及新账本阶段可复用同店缓存；失败查询和原价兜底不覆盖它，不把原价1系数伪装成后台成功记录 |
| `visits` | 账本、卡号、segment_id、完整入出场时间、创建来源、本次折扣来源（`latest/cached/original`）、两种精确系数、不可变四金额及摘要、查询/缓存依据、不可变结果JSON、本次金额分/时长、基础规则摘要；唯一仍为 `(ledger, card_number, entered_at, exited_at)`，不加入segment_id。本次实际金额成为后续段内重放的AppliedPrice；不复制历史完整配置或保留旧member_pricing |
| `reply_tasks` | 关联访问或错误消息、目标群、原消息 ID、发送机器人、待发文本、发送状态、返回的回复消息 ID或错误类别；成功账单唯一 `(visit_id, group_key)`，错误提示按来源消息唯一 |
| `group_recovery` | 按机器人、群、门店、阶段及广播QQ标识恢复上下文；保存首次绑定启用界线、可信锚点消息ID/时间、本轮固定上界、当前页游标、状态/错误及恢复代次。同一上下文只运行一个恢复任务；失败和中断不提前推进可信锚点 |
| `repair_jobs` | repair_id、kind（repair/restart）、门店/阶段/卡号/原segment_id、操作人/群/机器人、理由、状态/时间、预览和确认结果。repair保留来源操作列表、完整待处理摘要、价格及旧账差异；restart只保存旧段、影响统计、确认起点及新段关联，不要求逐源操作/选价。共用确认幂等和审计，不新增重开任务表；未知卡号误报仍可目标为空且仅ignore |

会员阻断由source_messages中当前活动段的未解决问题推导；封存段原错误/状态保留，段状态决定其不再参与新段结算或阻断，不另加一套来源重开状态。未知卡号及group_recovery未完成分别构成门店阻断，重开不清除它们。修复后保留原错误及repair_id，解决类型为ignored_false_positive、duplicate或corrected；普通来源状态仍用received/retry_wait/paused/needs_review/settled/duplicate/ignored_before_ledger。尚未落库输入仅暂存内存，不宣称持久化；数据库不保存后台密码、Cookie或Token。

已结算记录及其结果不因再次计算、昵称变化或配置编辑而被覆盖。发送成功与否不是支付状态，数据库也不将应收标成“已支付”。历史不自动过期或按天清理；人工归档须保留完整账本，不能留下仍在活动阶段中被截断的历史。

### 6.3 原子处理和发送边界

1. 来源及候选校验通过后，持久化原正文、纯文本标志和 `received` 状态；已有补拉栅栏时只接收，不提前结算。原文作为单份证据保留，规范化字段另存。来源暂时写入失败则保留内存输入、冻结可信接收锚点、挡住该店后续结算并有限重试。成功保存的正常来源与接收锚点在同一事务更新；存在已知缺口时不推进锚点。传输键冲突复用已有状态，账本前旧消息仍先忽略，不因旧正文格式阻断。
2. 先按已存状态排除重复或明确冲突，并由第5.3节队列取得处理次序；对有效新访问，在写事务之外调用一次本店会员查询。成功使用最新折扣；可预期的会员查询异常交由事务中的同店同卡缓存/原价选择，不在会员失败后暂停计费或反复登录。全部后台请求在工作线程运行，不持有SQLite写锁，不在异步handler中直接执行同步HTTP。
3. 处理任务打开独立连接，使用 `BEGIN IMMEDIATE` 再次核对跨段去重/已出账冲突、目标段仍活动、段内较早来源、顺序及带原价格的完整段内历史；查询失败时在事务中读取有效缓存，无缓存用两种1系数，再构造本次配置并计算。数据库忙等待5秒，临时存储错误按第6.5节处理；前置检查不能替代本事务终审。
4. 核心成功后，将成功查询的折扣缓存更新（若有）、本次有效价格快照、有效访问、不可变结果、来源关联及本群 `pending` 回复任务一起提交；计算或写入失败时不留下“已有效但没结果”的访问。历史快照不覆盖，失败查询不更新成功缓存；事务内不请求后台。
5. 确定的业务异常回滚候选访问，再记录历史待核对及错误提示任务；临时错误保留来源并按第6.5节处理，不写成永久历史错误。数据库不可写时记录脱敏系统错误，不声称处理成功、不回复0元；单次重试不逐条向群报错，耗尽或明确错误后才提示未完成。无法持久化提示任务时不承诺提示最多一次，也不得因此放行后续收费。
6. 发送前核对原授权，有关联段时须仍活动，用条件更新把任务从pending改为sending并提交，再调用OneBot API；未确认领取提交前绝不发送。未知卡号门店错误提示不要求虚构一个段。封存段pending保留并暂停自动发送；已领取的sending不能假称撤回，按既有成功/失败/不确定语义收尾。网络不放入事务，成功才保存sent及消息ID；状态保存可有限重试数据库操作，不自动重发API。

SQLite 事务及唯一键负责最终并发一致性，不只依赖进程内锁。同步数据库操作和核心重放放入工作线程，连接在该线程创建和关闭，避免阻塞 NoneBot 事件循环。摄像头任务和计费任务没有共享业务锁。

部署固定以现有单机、单个机器人进程和一个持久化SQLite文件为边界；同进程多个机器人账号仍按传输键记录、按访问和群去重。内部异步任务及工作线程复用该进程，不新增中间件、其他服务、多副本或跨数据库实例执行路径。

### 6.4 恢复及幂等

| 恢复点或重复情况 | 规定行为 |
|---|---|
| 消息已保存为received/retry_wait或可恢复paused就退出 | 先恢复群历史覆盖及归类积压，再与实时消息进入同一队列；原账本、原规则和原授权必须仍有效，已有金额不重写 |
| 来源尚未保存，只在内存中就退出 | 从故障前可信锚点补拉原事件，不承诺必定找回；失败保持恢复阻断，管理员核查；完整恢复沿用原账本，确认无法补齐才按Q8处理 |
| 访问与结果已经提交，回复尚为 `pending` | 原授权及计费段仍活动时读取保存结果恢复发送；段已封存则保留暂停，不追加访问或重新收费 |
| 已进入 `sending`，进程退出或发送超时 | 改为 `uncertain`，只保留发送核对，不自动重发、不阻断后续新计费 |
| API 明确拒绝发送 | 标记 `failed`，保留计算结果，不回滚访问、不自动重发、不阻断后续新计费 |
| 发送成功但 `sent` 状态写入失败 | 仅有限重试保存状态，绝不再次调用发送；耗尽或进程退出后无法确认落库时转 `uncertain`。不能保证平台消息和本地事务同时提交，不承诺跨故障严格只发一次 |
| 同一来源消息再次投递 | 返回已存状态，不开启并行处理或重置重试预算；已 `sent`、`failed` 或 `uncertain` 的回复不自动再发 |
| 同一访问在另一群精确重复 | 复用同一结果，创建该群唯一回复任务，引用该群原消息 |
| 机器人离线或未连接 | 尚未开始发送的任务保持 `pending`，在原机器人连接后处理，不切换账号猜测发送 |
| 群/计费开关关闭、来源调整、群改绑门店、账本切换 | 当前条件不再授权的待处理或待发送任务暂停，保留原状态，不改归新门店、不补发旧阶段消息 |
| 补拉任务只保存了部分页就退出 | 已存来源保留，可信锚点不前移；下次从最新页重建游标并按原范围去重补齐，完整覆盖前不放行门店结算 |
| 修复预览后退出或确认期间退出 | 仅预览不改变历史；确认提交按repair_id核实是否applied，未提交则整笔回滚，已提交不重复新增访问/回复 |
| 单卡重开期间退出、重复确认或普通重启 | 切段与restart单applied在同一事务；重试先查repair_id，已应用直接返回原起点/新段。重建后继续原新段，封存段不恢复自动结算/发送、不再阻断新段 |

恢复入口复用同一服务；启动/连接只恢复活动段任务，封存段保留审计。无常驻轮询或定时重算，重复消息/连接不重置预算。恢复/发送须重查启动快照、原群绑定/门店/阶段、段活动状态及原机器人；配置变更仍通过重启，Q22段切换只持久化到SQLite并立即供同一服务使用，不写配置文件。待发队列按已有顺序执行，不并发重复领取。

无法仅靠数据库保证网络发送的恰好一次，Q5 已选择“结果不确定时人工核对”。因此 `sending → uncertain` 是明确的故障语义，不增加普通文本回复回退，也不通过重新投递触发第二次发送。

### 6.5 故障分类、有限重试和恢复条件

以下次数和状态划分为工程约束，不增加配置项。可重试的存储操作及历史读取的临时网络/HTTP错误，每次最多3次（含首次），等待1秒、3秒；历史读取的权限/不支持/无效响应直接失败，客户端不叠加重试。会员查询每个正常新访问调用一次，可预期异常立即用Q17缓存/原价；显式管理员预览/确认各自是一轮独立准备，不是自动重试。SQLite忙等待5秒；所有等待和网络均不持写事务或阻塞事件循环。后台超时仍按每次HTTP请求，多页查询总耗时不等于等待间隔。

| 分类 | 处理、影响范围及恢复 |
|---|---|
| 临时存储故障 | SQLite `BUSY/LOCKED` 按上述次数重试；只读目录、磁盘满或I/O写入失败同样只作有限尝试，不能宣称存储已恢复。原消息已持久化且可定位卡号时挡住同卡后续结算；来源未能持久化时挡住该店后续新结算；共享数据库持续不可用时所有使用它的门店都会受影响 |
| 重试耗尽 | 原输入仍完整时置为 `paused`，原因记为 `transient_exhausted`，不是历史损坏；停止自动尝试，排除故障后通过维护重启开启一轮恢复。不得因后续消息或重复连接不断重新尝试；不要求仅因次数耗尽就换账本 |
| 可预期会员查询异常 | 既有公共函数抛出的 `MembershipError` 子类，包括超时、连接/HTTP错误、认证失败、精确卡号不存在、同源限制或页面/折扣解析错误，统一记录脱敏诊断后按Q17选择缓存或原价；不设置卡号/门店暂停，不自动重登，也不返回虚假的后台成功记录 |
| 历史读取失败或覆盖不完整 | 保留group_recovery失败及门店恢复阻断，可重连或管理员重试；没有“无历史即视为无遗漏”的默认分支，也不把历史请求失败当成会员查询失败使用原价绕过 |
| 确定的历史问题 | 当前段非法/迟到/重叠置needs_review，阻断该卡；未知卡号或无法限定影响范围则阻断门店。重试/重启不清除。单卡可按9.4修复，或9.5确认封存旧段后继续新业务；整店问题仍按Q8处理。折扣及查询来源变化不属此类 |
| 核心与程序异常 | `BillingInputError`、`BillingConfigError` 保存稳定的 `code/field`，置为 `paused` 并核对，不循环重算；确认原始访问确有历史问题时转 `needs_review`。`TypeError`、`RuntimeError` 或其他未分类异常置为程序故障暂停，不纳入临时故障重试。完整输入仍在、修复无需改动已播报历史或固定计价规则时可重启恢复原任务，否则按历史问题处理 |
| 已保存账单的发送错误 | `reply_tasks.failed/uncertain` 仅表示回复失败或结果待核对，不写为来源历史失败，不设置卡号或门店历史阻断；已确认账单与访问保留，后续新访问继续计费 |

来源使用第6.2节统一状态及修复解决类型，等待前序或授权恢复保留原状态和等待原因。所有候选保留单份原文，待处理输入不得因后续到来被跳过。恢复状态属于group_recovery，修复单状态属于repair_jobs，发送状态属于reply_tasks，三者不替代来源历史判断。恢复任务用pending/running/complete/failed/authorization_paused；修复单用previewed/applied/rejected/invalidated/expired。

数据库提交报错后，重试前先按传输键、访问唯一键及已保存结果核实是否已经提交，再决定继续来源处理或复用结果；不得把一次提交结果不确定的写入直接当成未发生。对明确已提交的访问不再调用核心或重复建回复任务。会员异常直接按现有公开异常类型分类，不匹配异常文案，不再为已取消的“查询失败暂停/多次重查”增加临时错误分类接口。`TypeError`、`RuntimeError`、返回门店/卡号身份不符或本地数据库异常仍属于集成/存储故障，不能吞掉后假称会员查询失败而按原价结算。

**尚未落库的内存输入仍可能丢失。** 有限重试期间保留输入、冻结可信锚点，耗尽后暂停；维护重启前恢复存储并在正常关闭中有限保存。强退或掉电时不能依赖内存暂停，启动/连接恢复必须先补查原事件，不能仅见SQLite“没有失败行”就放行。补拉成功才恢复结算，失败保持恢复阻断并人工核对；不增加第二份来源日志，也不把手工修复当成可随意编造丢失事件的入口。

临时等待期间不逐次发错误提示；明确错误或预算耗尽时按第7节提示一次。暂停新计费不回滚既有有效访问，已保存账单的待发任务仍须满足原授权及发送状态要求；发送本身失败按 Q15 独立处理。

## 7. 成功回复和错误处理

成功回复固定为四项，并真正引用原始出场消息：

```text
会员卡号：4637
用户昵称：piment
本次在场：6小时22分钟
本次应付：78元
```

上述金额仅适用于无此前历史、日间内 6 小时 22 分钟的示例；同样的文字若出场时间或历史不同，金额可以不同。不能从第三行 `98(学生卡)` 推导应收，也不能只凭消息模板硬编码 78 元。

构造 `MessageSegment.reply(str(original_message_id)) + MessageSegment.text(body)`，发送至原群。原消息 ID 使用实际 OneBot ID，接受适配器合法的有符号整数，不与群号或用户 ID 混淆。引用消息不存在或平台拒绝时按发送失败处理，不发送没有引用的替代账单。

格式规则：

- 时长总是 `x小时x分钟`，小时允许大于 23，分钟范围 0～59；整小时仍显示 `1小时0分钟`，不足一小时显示 `0小时16分钟`。使用本次完整时长，不用当日累计时长；如展示函数收到更高精度秒值，仅展示时向下舍去不足一分钟部分，不改计算值。
- 金额从整数分转换，固定后缀 `元`，无 `¥`、无千位分隔符、不经 `float`。例如 `0` 分为 `0元`，`500` 分为 `5元`，`1250` 分为 `12.5元`，`1251` 分为 `12.51元`。
- 昵称来自消息正文；会员卡号按原字符串输出，不显示广播 QQ 的昵称或群名片代替会员昵称。
- 不附加累计消费、计费明细、后台地址、折扣、支付成功等本期未要求的信息。

错误处理矩阵：

| 情况 | 记录/计费行为 | 群回复 |
|---|---|---|
| 非群、总开关关闭、无本群配置、自动计费关闭、非指定 QQ、自发消息、非候选 | 不生成访问，不调用核心 | 无 |
| 当前段出场候选格式非法、0时长、含秒、非法时间 | 保存失败，能定位卡号则暂停该卡，否则门店阻断；明确属于封存段的旧来源按下行归档 | 引用原消息：“自动计费未完成：出场信息无效，请人工核对。”；无金额 |
| 完全相同的传输重复/本群访问重复 | 使用已有状态，不重复生成发送任务 | 不新增回复 |
| 消息时间早于本阶段启用界线 | 记录为账本前旧消息，不补计、不阻断 | 无 |
| 卡号及原时间明确属于封存计费段 | 原归属/问题留待核对，不新增访问或当前段阻断；重复复用旧状态/结果，不新增自动回复 | 无 |
| 当前段较早来源仍在处理或有限重试 | 保留后续输入，同段等待；来源未落库时该店等待，不越过本段前序 | 等待期间无逐次错误提示 |
| 非重复的迟到或重叠访问 | 保留问题，不写有效访问，暂停该卡号后续新计费 | 引用原消息：“自动计费未完成：出场记录冲突，请人工核对。”；无金额 |

| 临时存储错误 | 按第6.5节有限重试，成功沿用原账本；耗尽则保留原任务并可恢复暂停，不强制换阶段 | 单次重试无；耗尽时引用“自动计费暂未完成，请人工检查后恢复。”；无金额 |
| `BillingInputError` / `BillingConfigError` | 保存错误类别、`code`、`field`，不生成应收；暂停核对是否为输入或集成错误 | 引用未完成提示，不输出内部字段值 |
| 已配置后台但会员查询失败 | 用同店同卡最近成功保存的折扣；没有则两种1系数原价，保存失败类别及本次选价依据；不覆盖成功缓存、不暂停计费 | 计费成功后仍按固定四项格式回复，查询诊断不附加到群账单 |
| 同阶段内会员折扣或计价来源改变 | 本次采用新选择的有效配置，历史采用各自原价格，保留计时进度及实际已计费预算；不改旧账、不重开阶段 | 正常成功回复 |
| 程序异常或不可恢复存储错误 | 不循环重试或伪造应收；保留输入、诊断并暂停受影响任务，修复后须核对历史完整性 | 可发送时引用“自动计费未完成，请人工核对。”；无金额 |
| 回复发送失败/不确定 | 保留已计算访问与结果及发送状态，不阻断后续新计费 | 旧回复不盲目重发、不重复计费 |
| 历史补拉失败或覆盖未完成 | 保存群恢复状态，门店新结算等待，已有来源不丢弃；不自动重算旧账 | 仅向管理员管理响应或脱敏日志报告恢复问题，不为每条积压刷屏 |
| 修复预览拒绝或确认已失效 | 不修改原始来源、有效访问或账单，保留问题及差额报告 | 回复管理员具体原因，旧账差额不作为新成功账单发出 |
| 管理员确认单卡重开 | 仅切换该卡段并保存审计，不计算应收或假称旧问题已核平 | 回复管理员新起点、旧段留待核对数量及免费/封顶重置提醒，auto_cost关闭时明确说明 |

日志仅记录必要的消息定位、错误代码及阶段；不直接打印 Pydantic 错误对象、配置模型或后台异常响应。用户要求的卡号和昵称可以出现在对应成功回复中，不由本期擅自脱敏改变功能。

同步查询在后续业务服务中通过 `asyncio.to_thread` 执行，复用这一个公共查询函数，不再创建第二个异步抓取实现。本轮不新增 matcher、不修改核心、不查询真实账号。

### 8.3 有效配置与舍入

设原始小时单价为 `R` 分，某封顶为 `C` 分，后台返回普通计费系数 `b` 和封顶系数 `c`。后台的 `8折` 对应 `0.8`，不是 `8`：

```text
有效 hourly_rate_fen = HALF_UP_TO_INTEGER_FEN(R × b)
有效 day_cap_fen     = HALF_UP_TO_INTEGER_FEN(day_cap_fen × c)
有效 night_cap_fen   = HALF_UP_TO_INTEGER_FEN(night_cap_fen × c)
有效 early_bird.cap_fen = HALF_UP_TO_INTEGER_FEN(early_bird.cap_fen × c)
```

早鸟关闭时仍为 `None`；时段边界、免费秒数和步长不打折。乘法与舍入必须使用精确十进制或等价整数算法，并显式保证精度，不依赖全局 Decimal 上下文；不经 float。先将每个配置金额舍入到整数分，再调用核心，核心内部的步长费用舍入继续沿用现有算法，结果不再次乘系数。

默认20元/小时、日夜78元、早鸟30元，若“台费8折、自动计费7.5折”，有效配置为：小时价1500分、日间6240分、夜间6240分、早鸟2400分。原价15分钟免费规则不变；孤立日间16分钟应收15元、1小时15分钟18.75元、日间6小时22分钟62.4元。这些是后续编排测试的固定预期，不代表有效配置转换已在本轮编码。

0折、或很低折扣舍入后得到0分，都必须按0处理，不能强制变为1分。**当前核心价格及封顶校验仍要求正数，本轮未修改**；主体实施时须将核心相应金额字段扩展为允许0，并验证免费小时、步长、零预算、共享预算及返场行为。原始 `stores.billing` 仍要求正价格和正封顶，0值只来自已经确认的折扣转换。零金额支持完成前不得宣称会员折扣计费全链路可上线。

### 8.4 最新折扣、已存折扣和原价的唯一选择顺序

| 情况 | 本次采用的价格 | 缓存处理 |
|---|---|---|
| 后台明确未配置 | 原价，两种系数均为1 | 不查询，不用旧缓存覆盖人工关闭会员查询的选择 |
| 最新查询成功且完整有效 | 使用最新两种系数，0系数同样优先 | 成功结算事务中更新同店同卡成功缓存 |
| 最新查询抛出可预期会员异常，存在有效成功缓存 | 使用该缓存的两种系数 | 保留成功缓存，记录本次错误和缓存查询时间 |
| 最新查询失败，该店该卡没有有效成功缓存 | 原价，两种系数均为1 | 保存本次原价访问快照，不伪造或覆盖后台成功缓存 |

“新会员”在这里指该门店尚无成功折扣缓存的卡号；即使已有按原价结算的访问，后续查询仍失败时继续按此规则选择。缓存按 `(store_id, card_number)` 隔离，保留卡号前导零；跨群、重启和新基础账本阶段可复用同店同卡折扣，用当前账本基础价格重新换算有效金额，不继承旧阶段的计时或封顶进度。缓存不因状态、到期日或时间经过而自行作废，记录查询时间供核对；只接受成功查询的完整、合法两种系数，不跨门店或会员借用。

查询失败、原价兜底或查询来源变化不触发单卡修复、历史待核对或更换 `ledger_id`。后台认证、未找到会员及页面解析等可预期错误也按该顺序处理；配置结构错误和本地程序/数据库故障仍各自处理，不伪装成查询失败。群成功账单仍只显示四项，选价来源及脱敏错误保存到本地记录中。

### 8.5 逐访问价格、计时延续及变更后的封顶

取消每账本每卡只有一份固定 `member_pricing` 的设计；每条有效访问保存当时实际采用的系数、四个价格金额及选价来源，完成后不可变。固定时段、免费阈值及步长只在账本基础配置中保存，构造本次唯一配置时使用，不在每条历史中重复。后续获得最新折扣只影响当前及后续访问，不修改旧快照、旧应收或本地成功缓存的历史依据。`0.8` 与 `0.80` 数值等价，`latest/cached/original` 仅表示来源，不是需要暂停的计价模式切换。

调用方始终只构造一份当前有效BillingConfig，调用calculate_bill(visits, billing_config)。历史只读取当前段，每条携带原四金额，本次applied_price=None，唯一使用外层价格。核心在同一次无状态重放中还原本段进度；正常卡第1段自账本起点开始，重开后换成新段历史，核心无需知道segment_id。原价也走同一路径，不增加固定价兼容入口或在插件另算累计差额。

只传一份完整配置并不表示历史金额信息可以省略。如果只保留访问时间，核心无法区分“之前按20元计费”和“之前按16元计费”，就不能实现Q18保留原实际金额的规则；历史四个金额是重放事实，不是独立配置入口。计算成功后把本次配置中的四个实际金额保存为访问快照，供下一次读取。

计时上下文、首小时及完整步长的触发进度跨折扣变化保留；已经触发的收费节点不能换价后再次触发，0元正常计价也保留相应进度。当前访问新触发的首小时或完整步长费用按当前有效价格计算，未满步长的时间继续累计。每个日间、具体夜间及早鸟共享预算分别保留历史实际已计费金额，当前访问适用的新限额只约束后续新增费用，剩余额度取 `max(0, 新封顶 - 已计费金额)`；实际已计费可高于后来降低的限额，此时后续为0，不产生负金额或退款。封顶提高后在新剩余额度内继续按已有计时进度收费，不重新赠送免费时间。

固定待实现验收：先以原价在日间计费20元，再取得两种8折后日间封顶为62.4元，剩余额度42.4元；此前已计费78元而新封顶为62.4元时，当前同一日间实例新增应收为0，旧78元保持。分别覆盖缓存0折、原价兜底后首次取得折扣、折扣降低/提高、时段切换、早鸟共享预算和跨群返场，不把新系数套给过去访问。

后台请求在写事务之外执行，成功查询的价格可预先转换；失败查询则在结算事务内读取有效缓存并转换，随后完成最终历史核对。历史重放恢复每条访问的原价格。本地存储无法读取缓存或完整历史时仍不能假称会员失败而绕过存储错误；源消息时间仍是出场时间，查询时间仅作选价依据。

可恢复故障先修复依赖或存储，确认原始来源完整、规则未变，再维护重启并检查积压按序恢复；不把单次失败或重试耗尽作为换阶段条件。若原输入仅在内存，先恢复存储并按第6.5节正常关闭落库；尚未保存前不把杀进程重启作为无损恢复手段。历史完整性暂不能证明时先暂停核对，核对后能恢复则沿用，确认无法补齐才开新阶段。

部署时固定已经验收的NapCat版本或镜像digest，并记录历史接口能力；当前compose的latest标签在正式交付时须替换为验收版本，不为不同版本猜参数或加别名。用专用账本验证最新页、反向多页、包含边界、网关重启后的ID及真实引用。既有NoneBot SUPERUSERS配置明确修复操作者，不在群JSON再加名单；不支持目标历史接口的网关不算满足本期部署条件。

回滚代码须同时恢复匹配的配置文件，旧读取器不接受 `stores` 和 `auto_cost`。先停止自动计费并备份数据库，保留本次账本，不删除以制造“首次启用”。恢复新代码前核对回滚期间是否漏记；无法补齐则用新阶段。备份数据库须停机或使用 SQLite 备份机制，不能只复制一个正在使用的数据库文件并假设一致。

### 9.3 历史补拉：触发、分页、完整性与恢复

本期直接使用已部署NapCat的 `get_group_msg_history` 扩展，经当前OneBot机器人调用；不增加服务、客户端副本或其他适配器回退。实施时确认部署版本并记录版本号，验收分页方向、包含边界、消息字段与历史可用窗口；不支持或不能完成恢复时保留恢复阻断并明确报错，不能静默按“无遗漏”继续。

协议核验依据为[NapCat历史处理器](https://raw.githubusercontent.com/NapNeko/NapCatQQ/main/packages/napcat-onebot/action/go-cqhttp/GetGroupMsgHistory.ts)、[消息字段转换](https://raw.githubusercontent.com/NapNeko/NapCatQQ/main/packages/napcat-onebot/api/msg.ts)和[短ID映射](https://raw.githubusercontent.com/NapNeko/NapCatQQ/main/packages/napcat-common/src/message-unique.ts)。当前源码将消息ID作为不透明的分页定位值，短ID映射保存在内存；上游main的核验不能替代实际部署版本测试。本方案显式使用 `reverse_order`，不增加旧字段别名兼容路径。

| 触发 | 恢复下界与范围 |
|---|---|
| 启动、异常重启或OneBot重新连接 | 对实际启用的门店群恢复到最后一次可信接收锚点；同一连接代次只启动一个任务，原始输入和锚点均从SQLite恢复 |
| 来源落库失败、接收期间发生已知缺口 | 立即冻结该群可信锚点并建立恢复阻断；内存输入可先落库，存储与连接恢复后补查缺口，不用后来消息覆盖故障前锚点 |
| 新账本或首次新增群绑定 | 下界为账本创建秒值与该绑定首次有效启用秒值的较晚者；首个完整访问仍不裁切。新群不扫描其绑定前的全部门店历史，也不重置同店已有会员进度 |
| 管理员发现遗漏 | `计费补拉 重试`重开失败任务；`计费补拉 从 <北京时间>`核查当前群给定时间后的原事件。下界不得早于本绑定和账本启用界线，不导入首次启用前已结束的访问 |

恢复上下文身份固定为机器人账号、群、门店、ledger_id及广播QQ。普通关闭后重开同一绑定复用其界线与锚点；门店/阶段/来源/账号变更建立新上下文，旧任务保持原身份，不按新绑定迁移。变更前须核对旧积压；新上下文不会证明旧上下文的缺口已解决。

分页与提交顺序固定如下：

1. 在SQLite建立恢复状态后再允许受影响门店新结算。因为遗漏尚不能定位到卡号，恢复期间同店所有群只接收并保存实时候选，不提前查询/结算；其他门店继续。纯回复发送失败不建立此恢复阻断。
2. 首次请求用 `group_id`、`message_seq="0"`、`count=100`、`reverse_order=true`，并设置 `parse_mult_msg=false`、`disable_get_url=true`；响应只读取 `messages`。固定本轮最新消息作为上界，后来的实时消息保存在库中等待，不改变本轮范围。一次响应可能少于100条，条数不足不等于已补齐。
3. 从最新页向更早历史翻页。下一页将当前页最老消息的原 `message_id` 字符串填入请求的 `message_seq`；不对ID加减，不把 `real_seq` 或时间当请求游标。只用本轮API刚返回的游标定位，跨NapCat重启从最新页重新建立映射，再以数据库锚点识别已覆盖范围。
4. 对包含边界的重复消息按原传输键去重；校验页面顺序及边界确实向更早推进，原事件时间/发送者/消息ID完整，群和机器人身份正确。重复页、无进展、字段异常、方向不符、API明确错误或请求有限重试耗尽，均保留失败状态，不推进可信锚点；没有另一个宽松接口兜底。翻页持续至可信锚点被实际找到，或新绑定/人工时间范围的整页边界严格早于下界；不以随意截断的最近N条替代完整范围。
5. 每页授权候选使用原message_id/user_id/time/message，走同一规范化/持久化/解析及计费段归属规则；已存来源不迁移，落入封存段只归档，不重新阻断新段或查询会员。auto_cost关闭时显式补拉只保存授权范围，原QQ/门店/阶段校验仍执行，不放行自动结算。原时间不替换成拉取时间，不提取转发/图片内部正文或重发制造新时间。保存后先归类再按卡号/业务时间排队。
6. 页面覆盖及持久化完成后，原子推进可信锚点并解除恢复阻断；活动段needs_review仍生效，封存段问题保留而不阻断当前段。活动段补拉/实时积压进入同一队列，真正迟到仍转修复。单卡重开不改变群锚点或证明群缺口已完整。

每页读请求最多3次，等待1秒/3秒；一次恢复任务内不叠加客户端重试。中断后保留已经保存的来源，重连或管理员重试复用同一服务和去重键；无常驻轮询。补拉找到尚未结算访问时按处理时Q17选价，不捏造当时未知折扣；已有访问始终复用旧价格与结果。

找到锚点前历史已不可查、锚点消失、API仅能返回不覆盖缺口的窗口，均不能证明完整；保留受影响门店恢复阻断并提示人工核对，不自动换账本。即使API范围检查通过，也不承诺证明门店广播从未漏发或平台未返回被删除的内容。总群关闭时不执行；auto_cost关闭不自动补拉，管理员可显式读取现有账本对应缺口并保存来源，但不放行自动结算/回复。旧授权失效的自动恢复保持暂停。数据库/卷丢失时优先恢复完整备份，群消息不能替代全部旧价格和已出账结果。

### 9.4 第一版单卡修复：权限、预览与确认

管理入口复用NoneBot现有SUPERUSER，仅在明确绑定门店的OneBot群执行并受hyw总群开关控制；普通群管不自动获权。auto_cost关闭时可显式检查/修复当前活动段，或按9.5切换该卡段，但不创建/切换门店账本；自动结算/发送仍关闭。只打开原路径已有SQLite，数据库不存在、账本阶段关闭或规则不符时拒绝。封存段仅供查看/审计，本版不再对其补算或提交历史修复。

命令统一注册于现有插件，前缀沿用NoneBot的 `COMMAND_START`。`计费修复 查看 <卡号或门店> [页码]`查看该卡问题/账单或门店未知卡号问题，每页20条、默认第1页；`计费修复 预览 <卡号或门店> <修复JSON数组>`生成单；`计费修复 确认 <repair_id>`提交；`计费修复 记录 <repair_id>`查看审计。`计费补拉 状态/重试/从 <ISO北京时间>`使用相同权限和门店绑定规则。查看/预览不改有效历史、旧账或阻断，不自动发送成功账单。

| 操作 | 修复JSON及限制 |
|---|---|
| `ignore`：确认误报 | 显式提供source_id、action和非空reason，确认没有真实访问。可处理未知卡号误报，不创建虚拟卡号或有效Visit |
| `duplicate`：人工关联重复 | 显式提供source_id、action、已有visit_id、来源nickname及reason。目标须是本单同店/账本/卡号有效访问，允许引用封存段旧结果；原卡号未知时由目标及证据确定。只保存来源关联，不搬移原段或新增Visit；目标段封存时不新增自动回复。人工秒级镜像不改变自动精确去重 |
| `correct`：修正未结算输入 | 显式提供source_id、action、card_number、nickname、exited_at、duration_minutes及reason，来源已有合法卡号且与本单相同，不搬移身份。时间为秒精度UTC+08:00 ISO文本，时长为严格正整数分钟；昵称及区间过同一纯校验，不猜隐藏秒数、不改原始来源、不自填价格 |

JSON拒绝未知字段和重复source_id，reason非空且至多500字符。每单一店/一阶段/一卡/当前段；含correct新增访问时，操作须覆盖该段全部待核对及原授权暂停来源，正常同卡本段积压自动按原输入加入，不可任意覆盖或漏前序。纯ignore/duplicate可逐条解决，不结算正常积压，提交后交回同一队列；未知来源人工关联封存段访问只解决该来源，不重开旧段。存储/程序故障先修故障，不能ignore跳过。

第一版不编辑已结算访问、不跨身份、不自填价格。门店恢复未完成或仍有未解决的未知卡号来源时，不能证明该卡历史完整，不生成新增访问的可确认预览；纯ignore/duplicate仍可解决已存问题。未知源只可凭证据ignore或关联已有Visit，不支持凭空补一个身份及访问。没有原事件可恢复且确需更广的身份修正时保持人工阻断，属于第一版限制。原群后来改绑时，管理仍在原店当前绑定群处理原账本，旧群回复单独按原授权判断，不迁移归属。

预览与确认采用同一结算准备逻辑：

1. 固定原店/阶段/卡号/活动段、段内历史、全部相关未结算来源/问题集及门店阻断摘要；新增访问时，所有无法排序或非法来源必须由本单操作解决，不遗漏前序。correct形成规范化访问，原本合法待处理访问按原输入加入；ignore不计费，duplicate用目标保存结果，纯来源解决不查询会员或重放积压。新增访问按顺序Q17选价，成功查询形成同一拟提交事务的缓存视图，供后续失败查询按序选择；没有第二个缓存路径。
2. 先按5.2检查跨段已出账冲突，再构造当前段修复后完整有序历史，用同一核心按受影响访问前缀逐次重放，每次只传一份目标配置、其他历史带原AppliedPrice。新增访问四金额成为后续前缀事实；逐笔比较本段全部受影响旧账的current_payable_fen，新应收也由核心给出。旧JSON不覆盖，统计变化列入预览，没有第二套公式。
3. 出现重叠/非法输入、旧金额变化或无法完整核对时，记录拒绝原因及差额报告，不生成可确认的修复。已有账单包括已保存但未发送的账单，不能借“还没播报”绕过金额一致性约束。通过时保存previewed修复单、完整操作、价格依据、输入摘要、金额与阻断影响；有效期10分钟，绑定操作人及操作群。
4. 确认入口按kind选择repair或9.5的restart本地切段，复用同一权限/状态/审计处理。先查权限、操作群、阶段/段及单状态，已applied直接返回原结果。repair重新准备输入及选价，历史/来源/问题集/配置/实际金额变化则作废，段已切换也失效；同值系数/价格来源和读取时间变化只更新审计。restart不走本段选价和差额比较。
5. 取得同卡队列排他权后，在BEGIN IMMEDIATE内重查原段仍活动、完整输入/门店阻断摘要、操作来源未结算及单仍previewed；新增访问须覆盖完整且无未知卡号阻断，一次提交审计、来源关联、所有新访问/结果、按序成功缓存、唯一回复任务及applied。原文/原时间/发送者不覆盖，整单失败回滚，提交未知先查repair_id。
6. 提交后重新统计当前段剩余问题；本段无其他问题且门店无恢复/未知卡号阻断时，才恢复本段积压，不只翻转“已解锁”。封存段问题不计入此判断，其他卡问题不阻断本卡；全部未知源解决才移除相应门店阻断。auto_cost关闭时保留结果，启用后再处理自动积压。

ignore不产生账单；duplicate目标段活动且该来源群尚无任务时创建一个，引用原源并使用其昵称，目标段封存时仅保存关联。correct及本单合法待处理访问创建正常任务。旧提示/成功回复不撤回或重发，发送仍校验原机器人/原群授权及段状态，改绑后保持归属并暂停。审计保留操作人、理由、差异、价格及时间，可按repair_id查看。

第一版历史修复只提交旧金额全部不变的历史；有差额不提供强制修改/退款/调账，也不能ignore真实访问。管理员可另按9.5封存旧段并继续新业务，旧差额无需先解决；重开不把该差额改成已核平。

### 9.5 保底恢复：两步单卡重新起算

目标是在该卡旧账对不上、历史缺失或不再等待补齐时，快速恢复后续计费。权限、已有数据库/活动门店账本、群绑定、审计及确认有效期复用9.4；不新增管理服务、配置字段或一套计费入口。仅适用于库中已有活动计费段、影响可限定到该卡的情况；数据库/程序故障先修复，存在门店未知卡号、未归类/未落库来源或群恢复阻断时明确拒绝，并告知整店处理原因，不能靠重开单卡消除。

管理员只需两次操作（示例省略全局COMMAND_START）：

```text
计费修复 重开 4637
计费修复 确认 R123
```

第一条直接生成kind=restart的预览单并返回可原样复制、包含实际命令前缀及repair_id的确认命令；不需要另发查看、不填写JSON/来源ID清单/价格或起点。可在卡号后附原因，最长500字符；省略时记录“历史不完整，管理员确认重新起算”及当时系统问题摘要。查看与审计仍用原命令，不增加重开别名或独立确认命令。

预览只读取本地状态：显示门店、卡号、当前段、旧段待核对/未结算/待发送数量，并明确“旧账保留待核对，免费/计时/封顶重新累计，可能再次收费；以确认生效起点划分，首条跨起点访问仍计完整时长”。不查询会员后台、不调用历史API、不重放核心或比较旧账差额。预览统计是当前快照，确认涵盖生效起点前该卡旧段全部记录；正常到来的同卡来源只更新最终统计，不因此要求重复预览。授权、门店/账本/活动段或基础规则改变、预览超过10分钟时才需重新预览；会员折扣变化不使重开单失效。

确认复用同一卡号队列排他权，在一次BEGIN IMMEDIATE内终审权限、原活动段及门店阻断；记录生效起点T，封存旧段、创建下一活动段并将repair_id标为applied，保存操作人、原因、原/新段和最终影响统计。T采用确认时刻之后的下一Unix整秒（至多1秒），原事件时间仍按秒比较；须晚于现段起点及该卡已保存有效访问出场时间，时间异常则拒绝并提示核对时钟。预览不预设T，确认结果返回准确北京时间。不重写旧访问、原来源状态、结果或折扣缓存，不批量伪造“问题已解决”。任一写失败整笔回滚，提交未知先查repair_id，重复确认只返回第一次结果，不创建第3段。已准备的普通计算/修复终审须发现旧段失活而不能再提交。

确认后立即按同一规则运行，不需改JSON或重启：

- 已存来源保持原段。后到来源用原出场时间归属，`exited_at < T`属于旧段，`exited_at >= T`属于新段；有多次重开时按各段界线定位，不按接收/补拉时间搬移。缺少可信时间/卡号不能推断为旧消息，仍走正常核对。
- 旧段来源和问题只保留审计，停止自动结算及新增回复；旧段pending回复保留暂停，已发送不撤回，已sending按6.4收尾，failed/uncertain不重发。旧段积压和迟到旧消息不再阻断该卡新段。
- 跨段传输/业务去重和已出账重叠检查仍生效。新段核心只接收本段完整历史与一份当前有效BillingConfig；计时/免费/封顶从初始进度开始，折扣仍按Q17最新→缓存→原价，其他卡及门店ledger_id/规则不变。
- auto_cost开启且原授权有效时，服务直接处理新段来源；关闭时只保存切段结果，反馈“已重开，自动计费仍关闭”，不偷偷结算或发账单。重启沿用已保存的新段，不重新封存或恢复旧段任务。

成功响应只报告门店/卡号、新起点、旧段留待核对数量及重置提醒；不返回虚构应付金额。重开是管理员明确接受累计进度重置的保底，不自动触发、不承诺恢复原账金额准确性。若新段再出现新的历史问题仍按本方案处理；原群缺口和未知卡号问题需要整店恢复或Q8新账本，单卡重开不推进群锚点、不解除其阻断。

### 11.2 核心契约回归

2. 由真实广播来源发出至少各一条有第三行、无第三行的实际出场消息，人工复核反推入场、核心输入历史、本次时长和折后应收，现场检查是否真正引用原消息。确认原消息的结算金额及卡类别仍不参与计算。
3. 完成实际返场与再次出场，验证本次新增金额及门店共享历史；验证指定源以外的同文消息没有应收及回复副作用。
4. 普通重启后再验证返场和已处理消息的幂等；人为控制一次明确发送失败或连接故障，核对已保存结果及待核对状态，不用反复真实发账单制造故障。
5. 有多来源群时验证精确重复共享结果、每群引用各自消息；若真实广播时间不同导致重叠，必须按已确认规则转核对，不将此解释为自动去重成功。
6. 核验默认计费规则的日间、夜间、早鸟和边界样例。实际营业无法在一次验收中覆盖的跨夜/封顶场景明确列为待执行，不能用模拟历史冒称实际营业验证。
7. 验证后台失败有缓存用缓存、无缓存原价，恢复后最新折扣延续旧金额/预算；状态/到期日不限制折扣。存储/程序故障按暂停恢复验证，回复失败不阻断下一次计费。
8. 在专用测试账本中制造一次可控断线，验证多页缺口补齐、原ID/时间和真实引用、可信锚点推进及积压顺序；再重启NapCat验证游标及短ID映射边界。窗口不足场景如实记录失败阻断，不声称已补齐。
9. 用已授权SUPERUSER演练误报、人工关联重复及修正未结算输入的预览/确认，核对旧金额不变和该卡恢复；演练旧账出现差额被拒绝、越权及重复确认。原始证据、修复单及旧账均可追溯；不在营业账本制造真实损失来刷故障覆盖。
10. 在专用卡上保留一条无法修复的旧问题，演练重开卡号→复制确认命令，核对无需补齐旧账即可计费新访问、其他卡继续累计；再补拉旧消息和重启，旧问题不重新阻断，已出账访问不重复收费。检查重置提醒及审计，不在营业卡上无提示重置封顶。
11. 检查总群/auto_cost组合、人数回归、卷保存、备份及回滚。尚未落库就强退的风险优先用受控子进程验证，现场记录实际无法恢复的范围。

### 14.2 保留的边界与实施风险

1. 单机或同一持久化卷失效时无法保证持续写入；内存输入和群历史接口不能替代完整账本备份，也不能保证找回平台从未保存的事件。
