## 1. 目标、范围和确认记录

唯一业务链路：

```text
OneBot v11 群消息
  → 现有 hyw_assist 群开关
  → 本群 auto_cost 开关及真实发送者 QQ 校验，解析绑定的门店配置
  → 解析出场消息，以消息时间和展示时长重建完整访问
  → 门店账本内按卡号读取一致的完整历史、去重及校验顺序
  → 后台已配置时查询会员折扣，构造该会员的一份有效计费配置
  → 调用现有 hyw_cost.calculate_bill
  → 原子保存访问和本次应收
  → 引用本群对应出场消息，回复卡号、昵称、本次时长、本次应付
```

本期只计算并播报应收，并接入用户提供的只读会员查询模块；后台已配置时按已确认规则调整单价与封顶。后台未配置仍明确使用原价；配置后查询失败不退回原价。不执行扣费、收款、退款、订单修改或会员资料修改，不新增进场消息解析、计费查询命令、历史导入或自动更正功能。现有人数统计的摄像头配置、共享服务及忙碌锁保持现状。

以下 Q1～Q12 均为用户在本次对话中的明确答复，与历史方案的问题编号无关：

| 编号 | 已确认约束 |

| Q2 | 本期自动计费仅支持 OneBot v11，按实际发送者 QQ 号核验并使用真正的引用消息段 |

调用契约固定为：

| 项目 | 必须遵守的约束 |
|---|---|
| 入口 | 相对导入现有 `hyw_cost`，只调用 `calculate_bill(visits, billing_config)` |
| 访问集合 | 内置 `list[Visit]` 或 `tuple[Visit, ...]`；同一门店账本、同一卡号，从该账本开始至目标访问的全部有效原始访问 |
| 已出场记录 | `Visit(entered_at=..., exited_at=...)`，均为已闭合访问；不传 `as_of`，不创建虚构进场消息或未出场访问 |
| 本次定义 | 核心按入场时间排序后选择最晚一条。插件须先拒绝新收到的晚到历史，不能让核心把另一条访问当作本次 |
| 时间 | 确切的 `datetime`，时区为标准库 `datetime.timezone`；统一固定 UTC+08:00、`fold=0`，不用无时区时间或 `ZoneInfo` |
| 合法区间 | 出场严格晚于入场；不重叠、不重复；相邻访问的前次出场等于后次入场合法 |
| 日期域 | 转换为北京时间后位于 `0002-01-01` 至 `9998-12-31`，越界作为输入错误 |
| 本次金额 | 直接取 `BillResult.current_payable_fen`，是本次访问新增应收；不再次减去上次金额，不读取第三行金额或付款状态 |
| 本次时长 | 取 `BillResult.current_presence_seconds`，不能使用统计日累计时长代替本次时长 |
| 历史重放 | 每次传同一账本的一份固定规则和全部历史。付款、跨午夜、跨日、封顶及已播报均不是删历史的理由 |
| 核心异常 | `BillingConfigError`、`BillingInputError` 是业务校验异常；`TypeError`、`RuntimeError` 属于集成或内部错误，不伪装成免费结果 |

核心固定使用北京时间，日间和每个具体夜间分别封顶；没有整次访问或滚动 24 小时统一封顶。早鸟与基础时段、当日日间共享实际已收预算，不预占整份 30 元额度。插件层只将已确认折扣转换为有效单价及封顶，不另实现收费公式、套餐选择或封顶逻辑，也不在结果上再次乘折扣。

现有 Docker 为 Python 3.12，本次只读核验环境为 Python 3.13.11。`pyproject.toml` 当前声明支持 Python 3.8，但核心使用的 dataclass 参数等已不支持 3.8；实施时将运行版本声明对齐现有部署要求 `>=3.12, <4.0`，验证 3.12 和 3.13，不增加旧 Python 兼容层。

## 3. 门店配置与群绑定设计

### 3.1 唯一入口与完整示例

唯一配置入口仍为 `GROUP_CONFIG_FILE`，默认 `nonebot/plugin_data/group_config.json`，路径解析及启动快照机制沿用现有实现。`hyw_assist.stores.<门店ID>` 保存门店计费配置，`hyw_assist.groups.<群键>.auto_cost` 保存该群的门店绑定、开关和消息来源。同一家门店由多个群引用，规则、凭据和账本阶段只维护一份。

一个群最多绑定一家门店，一家门店可以绑定多个群；群内指定的广播 QQ 必须只发送该绑定门店的出场播报。本期不根据昵称、时间或消息第三行猜测门店，也不支持同一群混播多店后自动分流。摄像头参数继续使用已有配置入口，不随此次门店计费配置迁移。

以下为实施后的目标配置，当前读取器尚不接受，**本次不会写入现行示例、Schema 或部署配置**：

```json
{
  "hyw_assist": {
    "default_enabled": false,
    "private_enabled": false,
    "stores": {
      "hyw-store-001": {
        "ledger_id": "2026-11-initial",
        "backend": {
          "base_url": null,
          "username": null,
          "password": null,
          "timeout_seconds": 15,
          "allow_http": false
        },
        "billing": {
          "day_start": "12:00",
          "night_start": "22:00",
          "hourly_rate_fen": 2000,
          "day_cap_fen": 7800,
          "night_cap_fen": 7800,
          "first_hour_free_seconds": 900,
          "step_seconds": 900,
          "early_bird": {
            "start": "08:00",
            "end": "12:00",
            "cap_fen": 3000
          }
        }
      }
    },
    "groups": {
      "onebot11:123456789": {
        "enabled": true,
        "auto_cost": {
          "enabled": true,
          "store_id": "hyw-store-001",
          "broadcast_qq": "987654321"
        }
      },
      "onebot11:234567890": {
        "enabled": true,
        "auto_cost": {
          "enabled": true,
          "store_id": "hyw-store-001",
          "broadcast_qq": "876543210"
        }
      },
      "qq:group_a": {
        "enabled": true,
        "auto_cost": {
          "enabled": false,
          "store_id": null,
          "broadcast_qq": null
        }
      }
    }
  }
}
```

只要配置 `hyw_assist`，其 `default_enabled`、`private_enabled`、`stores`、`groups` 四项都必须显式填写。`stores={}`、`groups={}` 均允许；可以预先配置尚无群绑定的门店，但这些门店不启动账本。`hyw_assist` 整项未配置也仍合法，表示没有群自动计费配置。

所有现有 `hyw_assist.groups` 条目，包括关闭的群和 `qq:` 群，都在实施升级时补齐 `auto_cost`，且固定包含 `enabled`、`store_id`、`broadcast_qq`。关闭且未绑定时后两项为 `null`，无需创建虚拟门店或在群内复制规则；也可保留有效门店引用及来源 QQ 后关闭开关。

每个门店条目必须完整填写 `ledger_id`、`backend`、`billing`；`billing` 示例数值即用户要求的默认模板，程序不在缺项时静默补值。门店 ID 直接取 `stores` 的键，门店对象内不重复增加 `store_id`。

不保留缺少 `stores`、缺少群 `auto_cost`，或把 `ledger_id`、`backend`、`billing` 嵌入群 `auto_cost` 的旧结构作为兼容路径。其他插件保持原配置结构，禁止填写 `stores` 或 `auto_cost`。

### 3.2 字段与校验

| 门店字段 | 类型及约束 |
|---|---|
| `stores` | 必填对象，键为实际门店 ID，值为完整门店配置；允许空对象 |
| `stores` 的门店 ID 键 | 非空字符串，无首尾空白，区分大小写；作为门店唯一身份，不按名称、群号或整数转换猜测 |
| `ledger_id` | 必填非空字符串，无首尾空白，区分大小写；是门店内人工指定的账本阶段标识，不使用进程启动时间随机生成 |
| `backend` | 必填五字段对象，包含 `base_url`、`username`、`password`、`timeout_seconds`、`allow_http`；凭据三项全为 `null` 明确关闭会员查询，或三项全部填写后启用查询；不接受部分填写 |
| `backend.base_url` | 配置时为合法绝对 HTTP/HTTPS 后台目录 URL，不含内嵌用户名密码、查询参数、fragment 或空白；标准化为尾部一个 `/`。目录可用于限定门店，不能填成某个 PHP 文件地址。HTTP 须同时显式开启 `allow_http` |
| `backend.username/password` | 配置时非空；密码原样保留且使用 `SecretStr` 承载，不输出模型或配置原文，不保存到计费数据库 |
| `backend.timeout_seconds` | 必填有限正数，单位秒，拒绝布尔值及数字字符串；模板为15，作用于每次 HTTP 请求，不是整个分页查询的总时限 |
| `backend.allow_http` | 必填严格布尔值；模板为 `false`。沿用原模块的 HTTP 显式许可要求，HTTP 地址必须设置为 `true`，HTTPS 不要求此许可 |
| `billing` | 必填完整对象，字段与核心一一对应；不允许额外字段 |

| 群字段 | 类型及约束 |
|---|---|
| `groups.<群键>.enabled` | 沿用原有严格群开关，控制该群整个 `hyw_assist` 插件 |
| `auto_cost` | 必填对象，只允许下列三个字段，不保存门店规则、凭据或阶段标识 |
| `auto_cost.enabled` | 必填严格 JSON 布尔值，拒绝字符串、数字、`null` |
| `auto_cost.store_id` | 必填；开启时为与 `stores` 键完全相同的非空字符串，关闭时允许 `null`。只要不是 `null`，即使群或自动计费关闭，也必须引用已定义门店；不存在的引用阻止启动 |
| `auto_cost.broadcast_qq` | 必填；开启时为满足 `[1-9][0-9]*` 的实际发送者 QQ 号字符串，关闭时允许 `null`；非空时无论开关状态都须满足该格式。不按昵称、群名片或被引用消息作者匹配 |

开启自动计费的 `auto_cost` 只能出现在 `onebot11:` 群键下；`qq:` 群即使总群开关关闭，也不能配置 `auto_cost.enabled=true`。一个配置文件中可同时保留 QQ 官方适配器的其他群策略；OneBot 计费条目不会使 QQ 进程启用计费。自动计费不处理私聊、频道、频道私信、通知或机器人自身发送的消息。

实际执行须同时满足：插件已加载、现有群策略允许、本群有明确条目、`auto_cost.enabled=true`、绑定门店已定义、当前适配器为 OneBot v11、真实发送者等于 `broadcast_qq`。从 `stores[auto_cost.store_id]` 获取唯一的后台、规则和账本阶段。`default_enabled=true` 不会给未列出的群自动绑定门店。总群开关与自动计费开关互不替代；私聊开关不能启用自动计费。

`stores.<门店ID>.billing` 的具体约束：

| 配置字段 | JSON 表达及转换 | 默认模板 |
|---|---|---|
| `day_start` | 严格零填充的 `HH:MM`，00:00～23:59，转无时区 `datetime.time` | `12:00` |
| `night_start` | 同上，严格晚于 `day_start`；同时为日间结束及夜间开始 | `22:00` |
| `hourly_rate_fen` | 严格整数，`1..2**63-1`，单位分，不收元单位浮点数 | `2000` |
| `day_cap_fen` | 严格整数，`1..2**63-1`，单位分 | `7800` |
| `night_cap_fen` | 同上 | `7800` |
| `first_hour_free_seconds` | 严格整数，`0..3599` | `900` |
| `step_seconds` | 严格整数，`1..2**63-1`，不额外要求整除 3600 | `900` |
| `early_bird` | 显式 `null` 表示关闭；开启时完整包含下列三项 | 开启 |
| `early_bird.start/end` | 同日 `HH:MM`，`start < end`，不隐式跨午夜；允许与基础日夜时段重叠 | `08:00` / `12:00` |
| `early_bird.cap_fen` | 严格整数，`1..2**63-1`，单位分 | `3000` |

时段配置本期开放到分钟精度；首小时固定 3600 秒、计费时区固定 UTC+08:00，没有 `timezone`、`day_end`、单独夜间单价、整次统一封顶等字段。布尔值不能充当整数；拒绝浮点数及数字字符串。核心允许封顶低于小时单价，也允许早鸟跨基础日夜边界，不添加相反限制。

沿用标准 JSON、UTF-8 无 BOM、重复键拒绝、未知字段拒绝和错误位置脱敏规则。所有门店、群条目及非空门店引用都校验，包括未绑定门店、关闭群及当前未加载的业务插件；错误阻止启动，不忽略错误条目继续运行。配置更改须重启生效。

### 3.3 启动快照、门店引用与变更

- 在 `group_config` 内增加 `hyw_assist` 专属的严格类型，复用通用群开关结构；其他插件保持原校验。不把 `extra="forbid"` 改为宽松字典。
- 同一次读取中解析门店表、群绑定和群开关，快照保留递归不可变的门店配置及绑定；门店条目以只读 Mapping 提供给会员模块，密码值保持 `SecretStr`。提供按群键解析的单一接口，例如 `get_auto_cost(group_key)`。无群条目或 `store_id=null` 时返回 `None`；已绑定时返回该群的自动计费开关、来源 QQ 和所引用的门店配置，后者复用快照中的同一份对象，不为每群复制。业务插件不再次打开 JSON，也不自行拼接另一套门店查找流程。
- 配置模型属于基础配置层，不从基础插件导入 `hyw_assist.__init__`，避免触发摄像头初始化或产生循环依赖。插件只做 JSON 类型到核心模型的显式转换。
- 同店多群只引用同一个 `stores` 条目，自然共享 `ledger_id`、`billing` 和 `backend`；无需再维护跨群重复参数的一致性比较。各群的开关及 `broadcast_qq` 可以不同。
- 启动时校验所有非空门店引用存在；重命名或删除门店时须同步更新全部引用，包括关闭群。禁止在引用失效时按群新建门店、选第一个门店或忽略该群。
- 只对本进程至少有一个实际启用群的门店初始化账本；多个群只初始化一次。单纯在 `stores` 中预配门店、全部绑定关闭或当前运行于 QQ 官方适配器时，不因这些条目创建或切换账本。
- 对实际启用门店，将规范化的 `billing` 序列化并计算规则摘要。已有 `(store_id, ledger_id)` 的摘要不一致时启动失败，提示修改该门店的 `ledger_id`；不以新配置重放旧账本。更改一店规则只影响该店，其他门店仍使用各自独立配置。
- 群改绑门店不迁移已记录历史、既有应收或待发任务。待处理记录持久化接收时的门店和阶段；恢复前须确认该群仍绑定原门店、原阶段，改绑后的旧任务暂停，不能用新门店参数重新处理。改绑前先核对旧广播和积压，来源必须与新绑定门店一致。
- 关闭自动计费仍校验所填字段，但不初始化相应账本或发起任何网络请求。配置解析和客户端构造也不登录；只在处理有效新访问时查询已配置后台。人数统计仍遵守其原有初始化配置要求，本期不做独立加载重构。

## 4. 出场消息解析与时间重建

### 4.1 输入边界

仅从已授权发送者的 OneBot 群消息中识别候选：首个正文行以 `【` 开头且以 `出场了！` 结尾。其他消息静默跳过。候选消息解析失败才生成核对提示，避免对该 QQ 的所有聊天逐条报错。

正文统一将 CRLF 转 LF，移除正文首尾空行及各行首尾的空格、Tab；不合并中间空行，不跨消息拼接，不从转发、图片或被引用内容提取文字。只接受纯文本消息段，拒绝候选中的图片、转发、@ 等其他内容；读取群事件自身的发送者及时间。

必须完整匹配两行或三行：

```text
【4637】piment 出场了！
在场时长:6小时22分钟
结算金额¥:98(学生卡)
```

| 部分 | 明确规则 |
|---|---|
| 首行卡号 | `【`、一个或多个 ASCII 数字、`】`；按字符串保存，保留前导零，不限制为四位，不转换成整数 |
| 首行昵称 | 去除卡号后的首尾水平空白，保留内部空格及 Unicode 字符；非空、不得含控制字符；昵称与固定后缀 `出场了！` 之间至少一个空格或 Tab |
| 第二行前缀 | 固定为 `在场时长:`，冒号后允许水平空白；不擅自支持中文冒号、英文单位或其他模板 |
| 时长 | 非负 ASCII 整数组成的 `H小时M分钟`、`M分钟` 或 `H小时`。组合形式的分钟为 0～59；仅分钟形式可大于 59；总分钟必须大于 0 |
| 第三行 | 可以完全不存在；存在时须以 `结算金额¥:` 开头，其后文字不参与数值解析、卡类型判断或折扣判断 |
| 其他内容 | 额外行、正文中间空行、小数时长、负数、秒数、缺昵称、缺卡号、非法组合分钟等均不接受 |

正则需使用完整匹配及 ASCII 数字范围，不使用会跨行吞掉正文的 `.*` 或把全角数字视为卡号的 `\d`。昵称始终作为普通文本构造回复，不解析成 CQ 码。

### 4.2 权威时间来源和精度

1. 出场时间取 OneBot 事件 `time` 的 Unix 秒值，使用固定时区明确转换为北京时间；不是机器人处理时间、数据库写入时间或开发机日期。
2. `duration_seconds = total_minutes * 60`，入场时间为 `exited_at - timedelta(seconds=duration_seconds)`。保留事件时间本身的秒数，不把整条时间取整到整分钟。
3. 入出场区间采用 `[entered_at, exited_at)`；不插入离店间隙、不拆成伪造访问，也不按时段边界提前切记录，交由核心处理。
4. 消息中的整数分钟是本期认可的事实精度。即使广播来源隐藏了秒数，也不补造 `:59`、平均误差或宽限时长。
5. 缺失、非整数或越界事件时间，非法总时长，时间相减溢出，以及总时长 0，均不构造合法访问或返回金额 0。

例如出场消息时间为 `2026-11-02 18:22:37+08:00`，展示 `6小时22分钟`，则重建入场为 `12:00:37+08:00`，在场精确为 22920 秒。

## 5. 账本、身份和完整历史

### 5.1 账本阶段

- 账本身份为 `(store_id, ledger_id)`；用户身份为 `(store_id, ledger_id, card_number)`。昵称不是主键，群号及广播 QQ 也不是会员身份。
- `store_id` 来自群绑定所引用的 `stores` 键，`ledger_id` 来自该门店唯一配置；同店多群不创建独立账本。群增删或改绑只改变消息路由，不迁移历史或重新归属既有账单。
- 账本第一次被有效开启时，在本地数据库持久化创建时刻和规则快照；相同阶段重启复用，不能每天、每次启动或每次返场重建。
- 只接纳出场消息时间不早于该账本创建时刻的访问。首条访问的入场可以早于创建时刻，保存完整区间。启用前已经出场的消息不补导，也不以接收时刻伪装成新出场。
- 不同门店互不累计；同门店同卡号在本阶段的全部有效访问共享进度和封顶。卡号 `04637` 与 `4637` 是不同身份。
- 改价、更换门店规则或无法补齐漏记历史时，配置新的、从未使用过的 `ledger_id`。旧阶段关闭并保留；不得切回已关闭阶段继续追加。一个门店同时只有一个活动阶段。
- 新阶段不继承旧阶段的封顶、免费进度、付款或历史；这是明确的新账本业务边界，不宣称等价于会员真实终身历史。

临时关闭、断线及停机可能漏掉广播。恢复前须确认消息已完整补齐且可按序处理；不能确认时更换阶段。重启恢复持久化状态不代表系统能自动找回平台未送达的消息，本期不加入平台历史拉取或后台补录。

### 5.2 历史读取与去重顺序

每次处理在同一数据库事务的一致视图中完成以下判定：

1. 先检查传输消息键 `(adapter, bot_self_id, group_key, message_id)`；重复投递直接使用已有状态，不生成新访问或新发送任务。
2. 以 `(store_id, ledger_id, card_number, entered_at, exited_at)` 检查业务重复。完全相同的访问使用已保存结果，不再次调用核心累计；同一来源群已有回复任务时不追加任务。
3. 业务记录是新记录时，检查卡号或门店是否有未解决的核对问题，并检查它与所有既有有效记录的时间关系。迟到历史、部分重叠、包含、同入场不同出场等均拒绝。
4. 新记录必须在该会员现有访问之后；前次出场等于本次入场允许。同时间重复在第 2 步处理，不错误判定为迟到。
5. 读取该会员在本账本内截至本次的全部有效原始访问，再追加本次访问，构造核心模型。不开启核心的“安全后缀”优化，不按今天、午夜或付款状态截断历史。

跨群镜像的消息时间若相差几秒，会导致重建区间不同；严格按 Q7 提示冲突，不使用容差、昵称相似度或相同展示时长推定同一访问。跨群的精确重复分别引用各群首次收到的对应消息，每群最多一次；昵称采用该条来源消息解析的显示值。

历史候选无效时不写入有效 `Visit`。为防止后续计算继续漏计，该卡号进入待核对状态；候选无法定位合法卡号时，该门店阶段进入待核对状态。问题不影响其他门店；卡号级问题不影响本店其他卡号。普通非候选消息、已知重复和明确早于账本起点的旧消息不触发阻断。

本期不提供人工改单或解锁命令。人工核对若需要改变已播报历史，不在当前阶段静默修补并续算；保留证据、结束有问题的阶段，按 Q8 开新阶段后恢复自动计费。

## 6. 编排、持久化和并发

### 6.1 单一模块边界

在现有插件内扩展，职责划分如下；复用已提供并适配的会员模块，不新建平行后台客户端或第二个计费服务：

| 文件或模块 | 职责 |
|---|---|
| `infrastructure_plugins/group_config/hyw_config.py` | `stores` 门店配置、群 `auto_cost` 绑定及计费 JSON 的严格类型、字段和引用校验；由既有配置读取流程调用 |
| `infrastructure_plugins/group_config/config.py`、`service.py` | 按插件名选择对应配置模型，保留门店及群绑定的不可变快照，按群解析唯一门店配置；继续维持唯一群开关判定路径 |
| `plugins/hyw_assist/__init__.py` | 注册自动计费消息 matcher，接入启动、机器人连接及关闭生命周期；调用下列服务 |
| `plugins/hyw_assist/auto_cost/message.py` | 纯文本解析、规范化事件数据、回复文本格式化；不读数据库或请求网络 |
| `plugins/hyw_assist/auto_cost/repository.py` | SQLite 初始化、事务、账本、历史、核对状态及发送状态 |
| `plugins/hyw_assist/auto_cost/service.py` | 统一业务编排、构造核心模型、调用核心、协调回复和恢复；不实现收费算法 |
| `plugins/hyw_assist/hyw_membership.py` | 接收单店后台配置，执行只读会员查询并返回两种精确折扣及原始会员信息；本轮已适配，不计算账单 |
| `plugins/hyw_assist/hyw_cost/` | 继续使用用户提供的原始核心，不改造成 NoneBot 插件、不引入网络和数据库依赖 |

`auto_cost` 子包初始化仅做必要导出，不注册第二套 matcher。现有 `config.py` 的摄像头参数仍走原有入口，不能顺带迁移到 JSON。

自动计费 matcher 使用 `on_message`，优先级 5、`block=True`，只匹配来源及候选规则已经通过的出场播报。有效或异常候选均由本链路消费，避免昵称包含“音游几”等关键词时额外触发摄像头。普通消息不匹配此 matcher，关闭群由现有前置处理忽略，不阻断后续业务；均没有计费数据库及发送副作用。handler 统一通过服务发送，完成后返回，不另行回复。计费不占用人数统计的 `busy` 锁，不自行创建另一套群开关逻辑。

本期可以直接读取 OneBot 的 `time`、`message_id`，并构造 `MessageSegment.reply`；已经确认只支持 OneBot，不为 QQ 官方适配器增加空实现或用 @、文本前缀模拟引用。其他插件的适配行为不改变。

### 6.2 存储位置与数据

数据库固定为 `nonebot/plugin_data/hyw_assist/auto_cost.sqlite3`，相对现有 `PROJECT_ROOT` 解析，与工作目录及群配置文件自身位置无关。Docker 中对应 `/app/plugin_data/hyw_assist/auto_cost.sqlite3`，使用已有持久化卷，无新增路径配置。只在本进程确有可执行的自动计费群时创建目录、打开数据库。

使用标准库 `sqlite3`，通过参数化 SQL 操作，不引入新的存储依赖。保存 UTC 整数微秒或等价无损时间值；账本启用界线单独按 Unix 整数秒记录，与 OneBot 事件精度一致。展示和核心输入再明确转换为固定 UTC+08:00。

必要数据结构：

| 数据 | 必须保存的内容与唯一约束 |
|---|---|
| `ledgers` | 内部账本 ID、`store_id`、`ledger_id`、创建时间、活动/关闭状态、是否待核对、规范化计费快照及规则摘要；唯一 `(store_id, ledger_id)`，每店最多一个活动阶段，待核对仍占该活动阶段 |
| `source_messages` | 传输消息唯一键、原群、机器人账号、发送者、平台时间、接收时解析的 `store_id` 及 `ledger_id`、处理状态、错误代码、关联访问；`received` 时保存待解析正文及是否纯文本，完成后保存解析出的卡号/昵称/时长；失败候选保留最少的核对原文，不记录配置凭据 |
| `member_pricing` | 每账本每卡一份计价快照：原价/会员模式、基础规则摘要、两种折扣精确值、有效计费配置和摘要；首次类别、状态、到期日及查询时间作为依据。唯一 `(ledger, card_number)`，已计费快照不能静默替换 |
| `visits` | 账本、卡号、完整入出场时间、创建来源、计价快照关联、不可变计算结果 JSON、本次金额分、本次时长、基础及有效规则摘要；唯一 `(ledger, card_number, entered_at, exited_at)` |
| `reply_tasks` | 关联访问或错误消息、目标群、原消息 ID、发送机器人、待发文本、发送状态、返回的回复消息 ID或错误类别；成功账单唯一 `(visit_id, group_key)`，错误提示按来源消息唯一 |

会员待核对状态可由 `source_messages` 中未解决的、已关联卡号的失败记录判断，不为相同信息增加平行状态表。无法识别卡号的候选问题设置账本级待核对状态。数据库中不保存后台用户名密码、Cookie 或 Token；规则快照只含基础/有效 `billing` 和必要折扣依据，不序列化整个 `BackendConfig`。

已结算记录及其结果不因再次计算、昵称变化或配置编辑而被覆盖。发送成功与否不是支付状态，数据库也不将应收标成“已支付”。历史不自动过期或按天清理；人工归档须保留完整账本，不能留下仍在活动阶段中被截断的历史。

### 6.3 原子处理和发送边界

1. 来源及候选校验通过后，先持久化足以重建解析输入的消息正文、纯文本标志和 `received` 状态并提交，便于重启恢复。传输键唯一冲突直接读取已有状态；已知早于账本启用界线的消息先归为旧消息，不因旧正文格式问题阻断新阶段。成功解析并完成处理后可清除暂存正文，保留规范化字段及必要定位。
2. 先按已存状态排除重复或明确冲突；对有效新访问，在写事务之外读取本店会员折扣并生成有效规则。全部后台请求在工作线程运行，不持有 SQLite 写锁，不在异步 handler 中直接执行同步 HTTP。
3. 处理任务打开独立连接，使用 `BEGIN IMMEDIATE` 再次核对去重、顺序、完整历史和会员计价快照，然后计算及写入。数据库忙等待设为 5 秒，超时记录为可核对的系统失败，不无限重试；前置检查不能替代本事务的最终判定。
4. 核心成功后，将首次计价快照、有效访问、不可变结果、来源关联及本群 `pending` 回复任务一起提交；计算或写入失败时不留下“已有效但没结果”的访问。该事务使用一份一致的历史及已经读取的折扣，不在事务内再请求后台。
5. 业务异常回滚候选访问，再记录失败及相应核对状态和错误提示任务。数据库不可写时记录脱敏系统错误，不声称处理成功、不回复 0 元；若能发送，仅发送未完成提示，重复提示无法持久化去重时不承诺最多一次。
6. 发送前用条件更新把任务从 `pending` 改为 `sending` 并提交，再调用 OneBot 发送 API；网络发送不放在数据库事务内。只有成功返回才保存 `sent` 及回复消息 ID。

SQLite 事务及唯一键负责最终并发一致性，不只依赖进程内锁。同步数据库操作和核心重放放入工作线程，连接在该线程创建和关闭，避免阻塞 NoneBot 事件循环。摄像头任务和计费任务没有共享业务锁。

验收部署以现有单个机器人进程、一个持久化账本文件为边界；同进程多个机器人账号仍按传输键记录、按访问和群去重。不承诺跨独立数据库实例的去重或多副本主动部署。

### 6.4 恢复及幂等

| 恢复点或重复情况 | 规定行为 |
|---|---|
| 消息只记录为 `received` 就退出 | 重启后在原账本、原规则、原来源仍有效时恢复处理；同一卡号的待处理记录按业务时间排序，既有已结算历史不重写 |
| 访问与结果已经提交，回复尚为 `pending` | 读取保存结果恢复发送，不追加访问、不重新收费 |
| 已进入 `sending`，进程退出或发送超时 | 改为 `uncertain`，保留待核对，不自动重发 |
| API 明确拒绝发送 | 标记 `failed`，保留计算结果，不回滚访问、不自动重发 |
| 发送成功但 `sent` 状态写入失败 | 视为不确定发送；不能保证平台消息和本地事务同时提交，不承诺跨故障严格只发一次 |
| 同一来源消息再次投递 | 返回已存状态；已经 `sent`、`failed` 或 `uncertain` 的不自动再发 |
| 同一访问在另一群精确重复 | 复用同一结果，创建该群唯一回复任务，引用该群原消息 |
| 机器人离线或未连接 | 尚未开始发送的任务保持 `pending`，在原机器人连接后处理，不切换账号猜测发送 |
| 群/计费开关关闭、来源调整、群改绑门店、账本切换 | 当前条件不再授权的待处理或待发送任务暂停，保留原状态，不改归新门店、不补发旧阶段消息 |

恢复入口复用同一个业务服务，在启动及机器人连接时处理尚未开始的任务，不增加常驻轮询、定时重算或不受控重试。每次恢复或发送前重新检查当前启动快照、群绑定仍指向原门店及阶段、活动阶段和原机器人身份；配置变更通过重启体现。待发队列以已有消息顺序执行，不在连接回调中重复并发领取同一任务。

无法仅靠数据库保证网络发送的恰好一次，Q5 已选择“结果不确定时人工核对”。因此 `sending → uncertain` 是明确的故障语义，不增加普通文本回复回退，也不通过重新投递触发第二次发送。

## 7. 成功回复和错误处理

成功回复固定为四项，并真正引用原始出场消息：

```text
会员卡号：4637
用户昵称：piment
本次在场：6小时22分钟
本次应付：78元
```

上述金额仅适用于无此前历史、日间内 6 小时 22 分钟的示例；同样的文字若出场时间或历史不同，金额可以不同。不能从第三行 `98(学生卡)` 推导应收，也不能只凭消息模板硬编码 78 元。

构造 `MessageSegment.reply(str(original_message_id)) + MessageSegment.text(body)`，发送至原群。原消息 ID 使用实际 OneBot ID，接受适配器合法的有符号整数，不与群号或用户 ID 混淆。引用消息不存在或平台拒绝时按发送失败处理，不发送没有引用的替代账单。

格式规则：

- 时长总是 `x小时x分钟`，小时允许大于 23，分钟范围 0～59；整小时仍显示 `1小时0分钟`，不足一小时显示 `0小时16分钟`。使用本次完整时长，不用当日累计时长；如展示函数收到更高精度秒值，仅展示时向下舍去不足一分钟部分，不改计算值。
- 金额从整数分转换，固定后缀 `元`，无 `¥`、无千位分隔符、不经 `float`。例如 `0` 分为 `0元`，`500` 分为 `5元`，`1250` 分为 `12.5元`，`1251` 分为 `12.51元`。
- 昵称来自消息正文；会员卡号按原字符串输出，不显示广播 QQ 的昵称或群名片代替会员昵称。
- 不附加累计消费、计费明细、后台地址、折扣、支付成功等本期未要求的信息。

错误处理矩阵：

| 情况 | 记录/计费行为 | 群回复 |
|---|---|---|
| 非群、总开关关闭、无本群配置、自动计费关闭、非指定 QQ、自发消息、非候选 | 不生成访问，不调用核心 | 无 |
| 出场候选格式非法、0 时长、含秒、非法时间 | 保存失败；能定位卡号则暂停该卡号，不能定位则暂停该门店阶段 | 引用原消息：“自动计费未完成：出场信息无效，请人工核对。”；无金额 |
| 完全相同的传输重复/本群访问重复 | 使用已有状态，不重复生成发送任务 | 不新增回复 |
| 消息时间早于本阶段启用界线 | 记录为账本前旧消息，不补计、不阻断 | 无 |
| 非重复的迟到或重叠访问 | 保留问题，不写有效访问，暂停该卡号后续新计费 | 引用原消息：“自动计费未完成：出场记录冲突，请人工核对。”；无金额 |
| 已存在相关待核对问题 | 不忽略缺失历史继续计算 | 引用原消息：“自动计费未完成：历史记录待核对。”；无金额 |
| `BillingInputError` / `BillingConfigError` | 保存错误类别、`code`、`field`，不生成应收；问题转待核对 | 引用未完成提示，不输出内部字段值 |
| 已配置后台但登录/请求/会员查询/页面解析失败 | 保存会员异常类别及来源，暂停该卡号计费；不按原价或0元替代，不重试登录掩盖错误 | 引用“自动计费未完成：会员信息查询失败，请人工核对。”；无金额 |
| 同阶段内会员折扣或计价模式改变 | 不用新折扣重放旧历史，不修改已保存应收；暂停该卡号等待核对 | 引用“自动计费未完成：会员计价规则变化，请人工核对。”；无金额 |
| 程序异常、数据库错误 | 回滚本次有效记录写入，保存或记录脱敏诊断；未完成事项不可标为成功 | 可发送时引用“自动计费未完成，请人工核对。”；无金额 |
| 回复发送失败/不确定 | 保留已计算访问与结果及发送状态 | 不盲目重发、不重复计费 |

日志仅记录必要的消息定位、错误代码及阶段；不直接打印 Pydantic 错误对象、配置模型或后台异常响应。用户要求的卡号和昵称可以出现在对应成功回复中，不由本期擅自脱敏改变功能。

## 8. 后台会员信息与折扣接入

### 8.1 已适配的模块及配置接口

用户提供的 `hyw_membership.py` 已包含实际页面协议，本轮只在该模块上调整配置、门店身份和数据校验，不重建客户端。公共调用链为：

```text
群绑定解析得到 store_id 和门店快照
  → BackendConfig.from_store(store_id, store_snapshot)
  → 凭据三项均为 null：返回 None，明确使用原价模式
  → 凭据完整：fetch_member_discounts(config, card_number)
  → MemberDiscounts：门店、原卡号、姓名、类别、状态、到期日、两种 Decimal 系数
```

`from_store` 接受普通或只读 Mapping 中的 `backend`，要求五个字段完整、无额外字段；字符串密码转为 `SecretStr`，已包装密码保持类型。未配置时仍校验门店 ID、请求超时和 HTTP 许可。该适配器不重复解析 `GROUP_CONFIG_FILE`，也不代替未来基础配置层对整个门店/群结构的严格校验。

已删除模块原有命令行、密码交互和 `HYW_BACKEND_*` 环境变量读取；没有旧入口别名或回退配置。本轮没有扩展现行 `group_config` 读取器，正式快照入口仍待实施，所以当前只能由调用方显式注入门店配置，不代表线上已经自动查询会员。

同步查询在后续业务服务中通过 `asyncio.to_thread` 执行，复用这一个公共查询函数，不再创建第二个异步抓取实现。本轮不新增 matcher、不修改核心、不查询真实账号。

### 8.2 已有后台协议和隔离

| 步骤 | 现有模块行为 |

### 8.3 有效配置与舍入

设原始小时单价为 `R` 分，某封顶为 `C` 分，后台返回普通计费系数 `b` 和封顶系数 `c`。后台的 `8折` 对应 `0.8`，不是 `8`：

```text
有效 hourly_rate_fen = HALF_UP_TO_INTEGER_FEN(R × b)
有效 day_cap_fen     = HALF_UP_TO_INTEGER_FEN(day_cap_fen × c)
有效 night_cap_fen   = HALF_UP_TO_INTEGER_FEN(night_cap_fen × c)
有效 early_bird.cap_fen = HALF_UP_TO_INTEGER_FEN(early_bird.cap_fen × c)
```

早鸟关闭时仍为 `None`；时段边界、免费秒数和步长不打折。乘法与舍入必须使用精确十进制或等价整数算法，并显式保证精度，不依赖全局 Decimal 上下文；不经 float。先将每个配置金额舍入到整数分，再调用核心，核心内部的步长费用舍入继续沿用现有算法，结果不再次乘系数。

默认20元/小时、日夜78元、早鸟30元，若“台费8折、自动计费7.5折”，有效配置为：小时价1500分、日间6240分、夜间6240分、早鸟2400分。原价15分钟免费规则不变；孤立日间16分钟应收15元、1小时15分钟18.75元、日间6小时22分钟62.4元。这些是后续编排测试的固定预期，不代表有效配置转换已在本轮编码。

0折、或很低折扣舍入后得到0分，都必须按0处理，不能强制变为1分。**当前核心价格及封顶校验仍要求正数，本轮未修改**；主体实施时须将核心相应金额字段扩展为允许0，并验证免费小时、步长、零预算、共享预算及返场行为。原始 `stores.billing` 仍要求正价格和正封顶，0值只来自已经确认的折扣转换。零金额支持完成前不得宣称会员折扣计费全链路可上线。

### 8.4 历史一致性及失败处理

核心一次调用的一份配置会重放全部历史，因此同一账本同一卡号须保存一份不可变的 `member_pricing`。首次有效访问保存计价模式、基础规则摘要、两种折扣及有效配置；之后每次新访问核对当前结果，继续以同一有效配置重放完整历史。

同阶段内有效折扣或原价/会员模式改变时，不用新规则重算已播报历史，按Q5/Q8暂停该卡号并人工核对；需要变更时开启新阶段。其他会员可有不同折扣并各自累计，不改门店基础模板。系数比较使用精确数值，`0.8` 与 `0.80` 视为相同；昵称、状态、到期日变化，以及类别名称变化但两种系数相同，都不作为计价规则变化。

查询失败或不完整时不创建有效访问和金额，保存来源问题并引用提示核对；不能因后台失败切换到未配置模式。查询、价格转换在写事务之外执行，提交前再次检查同卡快照及历史，避免并发查询覆盖另一条已提交记录。源消息时间仍是出场时间，后台响应时间只记作读取时间，不改变访问区间。

### 11.3 持久化、故障和恢复

使用真实临时 SQLite 文件及真实核心，覆盖：

| 场景 | 验收断言 |
|---|---|
| 首次阶段及重启 | 创建一次；重启沿用历史和规则；数据库不存在时只有有效开启才创建 |

| 首条跨启用时刻 | 采用完整重建访问；启用前已结束的消息不导入；启用界线按秒比较 |
| 规则/阶段 | 同阶段改价启动失败；新阶段原子关闭旧阶段；不能重开已关闭阶段；新旧数据均保留 |
| 会员计价快照 | 同卡完整历史使用同一有效配置；原价/会员模式或折扣改变转核对；状态/到期日和数值等价的系数表示变化不改价；请求失败不覆盖已有快照或提交候选访问 |
| 完整历史 | 核心收到本账本全部有效访问，包括跨日、已经0元、封顶及已播报记录；不包含其他会员或其他账本 |
| 传输重复 | 相同消息顺序重发、并发重发、重启重发均不新增访问或回复任务 |
| 业务重复 | 不同 message_id 的相同访问、同群/跨群、不同机器人账号；访问及结果只有一份，每来源群最多一个回复任务 |
| 精确与冲突 | 相差1秒的重叠镜像不能模糊合并；部分重叠、包含、相同入场不同出场、晚到历史都转核对；首尾相邻合法 |
| 待核对阻断 | 卡号级问题只阻断该会员；无法识别卡号时阻断该店阶段；其他门店继续工作；不得漏掉问题后继续收费 |
| 并发返场 | 同一卡号两条新消息并发时，SQLite 锁、顺序检查和唯一键保证无重复历史；已结算后到达的更早访问拒绝；不同会员不会串历史 |
| 事务故障 | 在来源提交后、访问插入后、结果写入后、回复任务提交前分别注入故障；要么整笔结算提交，要么没有有效访问，源状态可追踪 |
| 进程退出 | 重建服务及连接后恢复 received/pending；发送前/发送中/发送返回后的退出分别符合状态机；必要时使用子进程证明非内存恢复 |
| 发送故障 | 明确拒绝为 failed，超时/连接中断/发送后落库失败为 uncertain；不自动再发，不回滚已结算记录，不伪造成功 |
| 恢复授权 | 配置关闭、来源变化、群改绑门店、账本变化或原机器人未连接时不越权补发；待处理及待发记录保留原门店，不按新绑定重算/迁移；重新连接不重复领取任务 |
| 存储异常 | 锁超时、只读目录、磁盘/提交错误；无半笔结算、无错误0元；数据库路径及现有Docker卷一致 |

发送采用明确的可控测试替身记录实际 API 参数；故障注入针对外部 I/O 和事务边界，不把业务算法替换成固定金额。平台成功发送但状态落库失败的测试必须验证“不自动重发”的边界。
