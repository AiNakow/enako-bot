## 1. 已确认的目标与范围

用户希望在现有 `hyw_assist` 插件内，使用配置好的计费收银系统、小程序后台的用户名和密码，读取需要的信息，经过处理后实现新功能。

当前已确认的是两个后台的数据读取和业务处理方向，尚未确认具体功能、字段、指令、统计规则、账号数量和权限。本方案围绕读取与处理数据展开；充值、扣费、退款、修改订单或会员资料等后台写操作没有进入本次已确认范围。

后续应先完成确认和资料核对，再选择首个具体查询功能打通完整链路。确认未回复的项目继续标记为待确认，不把建议自动转成最终需求。

## 2. 当前项目基础与约束

| 现状 | 对本方案的影响 |
|---|---|
| 插件实际目录为 `nonebot/src/plugins/hyw_assist/` | 沿用实际插件名称及加载路径 |
| `__init__.py` 通过“音游几／中二几／舞萌几”关键词触发图像人数与上机人数统计 | 新功能在同一插件中扩展；具体新命令待确认 |
| `config.py` 通过 NoneBot `get_plugin_config()` 读取 `PEOPLE_COUNTER_*`；凭据已使用 `SecretStr` | 延续同一配置入口，为两个后台分别增加命名空间 |
| 当前插件导入时无条件调用 `create_service()`，摄像头序列号为必填配置 | 若需要只运行后台功能，必须同时解除初始化对摄像头的强制依赖；见 Q06 |
| 项目已有 `httpx`，部署镜像也已安装 Playwright 与 Chromium | 接口接入优先复用现有依赖；是否使用浏览器取决于真实登录流程 |
| `_adapter` 已统一群／私聊识别、用户 ID、群 ID 和消息构造 | 新命令复用适配桥，业务层不依赖具体适配器事件 |

| `group_config.json` 严格拒绝 `config`、`credential_ref` 等额外字段 | 后台凭据和业务参数不写入该文件；本方案不预设修改其 Schema |
| `gsz-assist` 已有异步客户端及独立服务层 | 参考其职责划分，两个新后台的认证仍按各自协议实现 |
| 已挂载 `/app/plugin_data`，对应宿主机 `/opt/bot-data/plugin_data` | 确需持久化时可使用其中的 `hyw_assist/` 目录 |
| 插件 README 仍保留独立复制版人数服务说明，与实际插件入口不完全一致 | 功能实现时同步更新为实际使用说明 |

现有人数统计共用的摄像头、模型和忙碌锁继续服务于图像统计；新后台请求不与摄像头共用同一把业务锁。无需为本功能另建业务插件加载路径或适配器框架。

## 3. 建议的最小结构

```text
nonebot/src/plugins/hyw_assist/
├── __init__.py             # 命令、参数、执行权限、消息回复和生命周期
├── config.py               # 扩展现有 NoneBot 配置及能力初始化
├── cashier_client.py       # 新增：计费收银后台登录、会话和查询
├── miniprogram_client.py   # 新增：小程序业务后台登录、会话和查询
├── service.py              # 新增：已确认功能的取数编排和计算
├── models.py               # 新增：实际功能需要的数据与结果模型
├── person_counter/         # 现有人数统计实现
├── nonebot.env.example     # 更新无真实凭据的配置示例
└── README.md               # 更新实际配置、指令及限制
```

两个客户端各自管理所属后台的协议与会话。只有实际协议存在共同能力时才扩展已有抽象，不提前新增通用后台框架、统一认证基类或多供应商适配层。小程序后台暂指用户使用的业务后台，是否涉及微信公众平台或其他平台需由 Q02 确认。

主要执行路径为：

```text
实际消息
  → 现有 group_config 场景开关
  → 命令参数及执行权限检查
  → service 选择已确认的查询与计算
  → 对应后台客户端登录／复用会话并取数
  → 校验字段、统一业务口径、生成结果
  → 使用现有适配桥回复
```

权限拒绝或群开关禁止时，应在后台调用前结束处理。每项功能只保留一条主要执行路径；两个数据源需要组合时，在服务层显式编排。

## 4. 后台接入与会话管理

### 4.1 接入方式的确定

两个系统分别核对以下条件，再确定各自唯一的实现方式：

1. 有可用的官方 API／集成接口时，按其认证协议查询。
2. 没有接口文档时，检查正常网页登录及查询产生的请求，确认地址、参数、会话和返回字段。
3. 确认必须依赖页面交互才能完成时，再选用 Playwright。

上述是接入选型步骤，不是运行时的多级回退。不会设计“HTTP 出错便自动转浏览器”的隐藏执行路径。

仅配置用户名和密码不保证能够无人值守登录。验证码、短信／扫码、双因素认证、设备绑定、IP 限制、局域网访问及账号单会话限制均需核实；发现限制后，应按 Q04／Q05 确认可行流程，不能把验证码绕过作为默认方案。

### 4.2 会话与异常

- 每个后台复用自己的异步 HTTP 客户端和 Cookie／Token，两个系统不共享认证状态。
- 登录加锁，合并同账号的并发登录；有明确过期时间时提前判断有效期。
- 仅在该系统协议明确表示会话失效时，重新登录并重试原只读查询一次。不能把所有 HTTP 403 都解释为登录过期。
- 密码错误、账号禁用、权限不足、需要人工验证、限流、网络超时和响应结构变化分别报告；不无限重试。
- 配置校验在初始化阶段完成；建议首次实际查询时登录，避免导入插件时发生外网请求。后台临时不可达通过当前查询的错误反馈体现。
- 关闭机器人时释放客户端；若选用浏览器，同时关闭对应页面、上下文和浏览器资源。
- 建议首先只在内存保存会话。需要跨重启保存登录状态时，先按 Q13 确认，并明确存储位置、文件访问权限和失效后的行为。

## 5. 配置方案

以下字段为候选配置，最终名称、默认值和必填关系在确认后收敛；不要求用户现在填写真实密码。

| 候选配置 | 用途与待确认约束 |
|---|---|
| `HYW_CASHIER_ENABLED` | 是否启用收银后台能力；默认策略见 Q06 |
| `HYW_CASHIER_BASE_URL` | 收银后台地址；由实际接口决定基址，避免通过聊天参数指定任意请求地址 |
| `HYW_CASHIER_USERNAME` / `HYW_CASHIER_PASSWORD` | 收银后台账号；密码使用 `SecretStr` |
| `HYW_CASHIER_STORE_ID` | 接口确需门店 ID 时才加入，字段名称和类型以接口为准 |
| `HYW_MINIPROGRAM_ENABLED` | 是否启用小程序后台能力；默认策略见 Q06 |
| `HYW_MINIPROGRAM_BASE_URL` | 小程序业务后台地址 |
| `HYW_MINIPROGRAM_USERNAME` / `HYW_MINIPROGRAM_PASSWORD` | 小程序后台账号；密码使用 `SecretStr` |
| `HYW_MINIPROGRAM_STORE_ID` / 商户标识 | 仅在实际接口要求时保留相应字段 |
| `HYW_BACKEND_HTTP_TIMEOUT` | 后台请求超时；建议初始值 30 秒，待 Q11 确认 |
| `HYW_BACKEND_CACHE_TTL` | 可缓存查询的有效期；建议初始值 15 秒，可选 0 表示关闭，待 Q11 确认 |

配置继续通过 NoneBot 已解析的配置读取，不再调用 `load_dotenv()` 或额外读取另一套环境文件。修改配置后重启生效。

能力关闭时不创建对应客户端、不要求对应凭据、不注册该能力的命令；能力开启而必需配置缺失或格式无效时明确报错，沿用项目选中插件加载失败会阻止启动的约定。账号错误只能通过实际登录核实，应报告认证失败，不能伪装成没有业务数据。

若 Q06 确认需要无摄像头运行，调整现有 `Config` 的摄像头必填校验和人数服务创建流程：按能力验证、创建服务、注册响应器及清理资源，并更新人数相关启动测试。具体开关和默认值需确认后确定，现有 `PEOPLE_COUNTER_*` 仍作为人数能力的配置来源。

密码、Cookie、Token、完整登录响应不写入日志、回复、测试 fixture 或 Git 文档。`SecretStr` 用于减少意外打印，不等同于加密存储。部署凭据继续由现有环境配置注入，样例文件仅使用占位值。

## 6. 数据处理、业务口径与缓存

`service.py` 提供与具体消息事件无关的方法，客户端只返回经过校验的数据。仅为已确认功能定义模型及计算，避免把后台原始响应直接暴露给命令层。

| 规则 | 处理建议及确认项 |
|---|---|
| 数据字段 | 明确必需／可空字段、单位、枚举、分页和结束条件；缺失必需字段时报错 |
| 人数等指标 | 区分监控检测人数、计费在线人数、预约人数和实际上机人数；来源与定义由 Q08 确认 |
| 金额 | 使用整数分或 `Decimal`；币种、优惠、退款、充值与消费的统计关系由 Q08 确认 |
| 时间 | 明确门店时区、自然日或营业日、跨日结算、起止边界和时间字段含义；不能直接推定采用服务器时区 |
| 跨系统关联 | 优先使用确认后的会员／订单／门店稳定 ID；没有可靠对应关系时返回待关联状态，不能按昵称猜测匹配 |
| 多页查询 | 读取功能所需的完整页集；达到查询范围限制时明确说明，不能把第一页当作全量 |
| 多源结果 | 标注数据来源、业务数据时间及抓取时间；两个后台的独立请求不宣称为同一时刻的原子快照 |
| 无数据与故障 | 合法空数据可返回空结果；请求失败、字段异常不能返回 0 或假装空列表 |
| 单源失败 | 聚合功能失败时整体报错，或显式展示部分结果，需按 Q12 选择；不会静默补零或提供旧缓存 |
| 缓存 | 仅缓存成功且允许复用的查询；按后台账号／门店、功能及完整查询参数区分；缓存结果显示抓取时间 |
| 并发与限流 | 相同查询可合并在途请求；后台请求采用有界并发及冷却策略，阈值按接口限制和 Q11 确认 |

第一期建议按需查询，不默认增加本地历史数据库或定时轮询。

## 7. 命令与权限

具体命令名称、参数、帮助文本和回复示例由 Q01／Q10 确认，本文不将“营业额”“会员余额”“预约”等例子直接列为实施功能。

- 群／私聊识别、用户与群 ID、图片与 at 构造复用 `_adapter`。
- 继续接受现有 `group_config` 的插件级场景控制；新增敏感命令必须具有实际执行权限检查。
- 建议财务及会员数据初期仅允许配置的运营人员查询；可采用 `SUPERUSER` 或确认后的插件操作员列表，最终按 Q09 选择。群管理员身份不自动等同于门店经营权限。
- QQ 指令面板元数据只控制面板显示配置，不能代替执行鉴权；注册面板项时明确描述、场景和管理员标记。
- 群内是否允许展示个人手机号、余额、消费明细等字段，以及是否需要脱敏／只允许本人查询，按 Q09 明确。
- 如需用户查询自己的会员数据，先确认账号绑定与归属验证方式；不能仅凭输入姓名或手机号就认定为本人。
- 如果不同群需要不同门店，另行设计插件自己的群与门店映射，使用含适配器前缀的群键；不向现有 `group_config.json` 塞入业务参数。

## 8. 条件性扩展：存储、历史与推送

以下内容只在用户明确需要时进入实施范围。

| 能力 | 进入范围后的改动 |
|---|---|
| 多账号／多门店 | 按账号隔离会话、缓存和门店权限；确定凭据配置结构；不在单账号需求下提前构建账号注册框架 |
| 群与门店绑定 | 增加插件自有映射及维护方式，决定用静态配置还是 SQLite，并覆盖跨群访问隔离 |
| 历史趋势／跨重启统计 | 增加 SQLite 数据模型、去重与更新策略、保留期限、备份和清理；运行数据放在 `plugin_data/hyw_assist/` |
| 定时报表／提醒 | 增加调度、目标群、时区、运行记录、去重及失败处理；同时核实当前部署适配器的主动消息条件 |
| 跨重启登录 | 明确必要性、可持久化的会话格式、文件位置和失效流程；不默认保存明文密码副本 |

定时推送不经过消息预处理器，不能只依赖现有 `group_config` 预处理器。若确认需要推送，发送前须主动检查目标群开关及对应功能权限，并明确错过任务后是否补发。

| 业务计算 | 已确认的金额、时间边界、退款／取消等状态、跨日口径、关联缺失、重复记录、多源部分失败 |
| 缓存与隔离 | 缓存命中／过期、不同参数／账号／门店隔离、错误不缓存、并发查询、数据时间展示 |
| 权限与分发 | QQ 与 OneBot 真实 `handle_event()` 分发；允许／禁止群、私聊、用户权限；拒绝时后台零调用；面板标记不代替鉴权 |
| 现有回归 | 人数统计成功、忙碌、失败、一次抓拍／推理及关闭；插件加载、群开关及既有测试 |
| 条件功能 | 若加入存储、绑定或推送，补充重启、去重、跨群隔离、开关检查、时区及失败场景 |

HTTP 接口使用可注入的客户端和脱敏响应测试；如果实际选择浏览器流程，为实际页面交互另设验证。默认自动化测试不依赖生产网络、不读取或改写真实部署配置。

### 11.2 覆盖率报告

每阶段报告受影响模块的行覆盖率、分支覆盖率、功能链路通过／失败／未执行情况及未覆盖原因。最终分别报告新后台模块、整个 `hyw_assist` 和完整测试套件结果；不能将新增模块覆盖率当作全项目覆盖率。

如包含启动子进程，覆盖率应实际采集并合并；如真实接口或浏览器测试未执行，明确标记跳过原因。数值门槛见 Q15，未确认前不将某个建议百分比当作验收承诺；已确认功能的正常与关键错误链路必须覆盖。

本次仅修改文档，没有实施新功能或重新运行业务测试，因此没有本方案的新覆盖率数据。归档记录中的历史结果不能作为新功能已通过的证据。

### 11.3 真实场景闭环

真实验收应在确认后的环境中逐项记录：

1. 通过实际允许群或私聊发送已确认的命令。
2. 使用配置账号完成真实后台认证和查询，核对门店与查询时间范围。
3. 将业务结果与同一口径的后台页面或导出数据对照，记录来源、抓取时间和差异。
4. 在实际会话过期后验证受控重登，确认失败反馈不会泄露凭据。
5. 验证禁止群和无权限用户无法触发后台查询；若有个人数据，核对脱敏与归属限制。
6. 若启用组合查询、持久化或定时推送，分别完成对应真实链路。
7. 回归原有人数统计；若允许关闭摄像头，验证关闭时后台功能仍能运行。

每条记录标明环境、适配器、结果和未执行原因。两种适配器均做自动化分发测试；没有真实环境的适配器如实记录限制。真实接口取数成功与实际消息回复闭环分别记录，不能用 mock 成功替代线上验收。
