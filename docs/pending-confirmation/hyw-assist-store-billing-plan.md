# hyw_assist 每店配置与进出场计费方案

整理日期：2026-10-19。

状态：**本轮讨论结果已落盘，尚未开始功能实现。** 用户已确认的规则与本轮方案采用的解释分别记录；公式和示例属于设计依据，不代表业务功能或真实链路已经通过验收。

本文件是后续每店配置、首个进出场计费功能的主要方案。[原后台接入方案](hyw-assist-backend-integration-plan.md)保留为讨论背景，不再并行维护当前实施方案，也不再要求按原 Q01～Q15 清单逐项确认后才能推进。正式开始实施时，移动本文件到 `in-progress/plans/` 并同步更新引用。

## 1. 本期目标

先完成每家店的独立配置，再在配置基础上完成首条业务链路：

```text
指定群、指定 QQ 的进场／出场播报
  → 校验来源、解析事件并去重
  → 查询计费后台和音屋小程序后台，核对会员及对应记录
  → 保存标准进出场记录
  → 按累计记录计算应付及本次新增金额
  → 保存结算明细并播报
```

在现有 `nonebot/src/plugins/hyw_assist/` 内扩展，每项功能保留一条主要执行路径。两个后台各自负责认证和取数；业务服务统一完成记录关联、结算和播报。后台接入范围为读取，不包含扣费、退款、修改订单等写操作。

## 2. 每店配置

沿用 NoneBot 已解析的配置入口，以门店唯一 ID 统一选择摄像头、后台账号、消息来源和计费规则。

| 配置 | 内容 |
|---|---|
| 门店身份 | 唯一门店 ID、名称、门店时区 |
| 摄像头 | 设备、通道、访问凭据及该店识别区域 |
| 计费后台 | 登录地址、用户名、密码、后台门店标识 |
| 音屋小程序后台 | 登录地址、用户名、密码、后台门店标识 |
| QQ 来源 | 适配器、来源群、允许的播报 QQ |
| 播报目标 | 结果发送到哪个群 |
| 计费规则 | 时段、小时取整、套餐和封顶规则 |

具体配置字段名在实施时统一确定。密码使用 `SecretStr`，真实密码及会话凭据只保存在部署配置或运行环境中，不提交到 Git，不输出到日志或 QQ 回复。

原有摄像头配置和调用同步迁入门店结构，更新调用方、示例与测试，不维护全局配置和门店配置两条并行路径。摄像头与后台能力分别校验，允许先配置后台功能而暂不配置摄像头。门店时区显式配置，不能直接采用部署机器或开发机器时区。

沿用现有适配桥及 `group_config` 插件级开关；来源校验使用真实发送者标识，不依赖昵称。门店业务配置不写入 `group_config.json`。

## 3. 进出场记录与后台核对

QQ 消息负责触发处理。会员身份、实际入场和出场时间，应在核实两个后台真实字段含义后确定来源，不能用机器人收到消息的时间直接替代业务时间。

跨系统优先通过稳定会员 ID、订单 ID 或已确认的映射关联。两个后台的同一条业务记录只生成一条进出场记录，不把两份来源重复累计。关联不唯一、时间冲突、缺少入场记录或后台查询失败时，保留待核对状态，不能按昵称猜测，也不能返回金额 0 假装核对成功。

使用本地 SQLite 保存以下必要信息：

- 来源消息标识、事件类型、业务时间和处理状态。
- 门店、稳定会员标识、后台记录关联、实际入场和出场时间。
- 结算周期、规则版本或快照、累计时长、计费小时数、封顶减免和应付明细。
- 此前已确认的累计应计金额，以及播报状态。

进场登记记录，出场核对并闭合记录；重复消息、后台记录重复返回和重启重试均不得重复累计。首次接管某会员时，要补齐相关计费周期内已有记录；重启后恢复未完成处理并核对更新，保证封顶所需历史完整。

暂时查不到后台记录时，可以按明确的有限重试策略继续核对，未完成前保持待核对。数据修正后重算受影响周期，保留更正依据并明确更正播报。实际播报失败保留发送状态，不把发送失败当成计费失败重复生成费用。

## 4. 本轮计费规则

### 4.1 用户明确确认的内容

| 规则 | 本轮确认结果 |
|---|---|
| 日间 | 12:00–22:00，20 元／小时，78 元封顶 |
| 早鸟 | 08:00–12:00，30 元一次性费用，可计入日间封顶 |
| 夜间 | 22:00 至次日 12:00，20 元／小时，78 元封顶；08:00 后与早鸟的关系按下列规则处理 |
| 小时取整 | 每个完整小时后的剩余时间，不超过 30 分钟舍去，超过 30 分钟计一小时 |
| 重复进出 | 同一人的日间／夜间封顶累计，离店间隙不算游玩时间 |
| 累计后取整 | 同一时段内两次各玩 20 分钟，合计 40 分钟后收 20 元，不逐次分别取整 |
| 夜间进入早鸟 | 12:00 前最多到 78 元；不到封顶时，早鸟按 30 元处理 |
| 早鸟抵日间的例外 | 用户原话：“夜间时段已封顶则不抵扣” |
| 已明确的样例 | 07:00–13:00 为夜间 20 元＋早鸟 30 元＋日间 20 元，共 70 元 |

### 4.2 本轮方案采用的具体解释

以下是上一轮方案已经写明、用于推导公式和验收样例的解释，不能表述为用户逐个确认过所有衍生例子：

1. 早鸟使用任意正时长即触发一次 30 元，同一人当天反复进出只触发一次。
2. “夜间已封顶”包括夜间加早鸟补差达到 78 元的情况。达到后，早鸟归入夜间封顶套餐，不再抵扣日间；未达到时，早鸟 30 元计入日间封顶。
3. 同一会员在同一结算周期内的有效记录共同累计，封顶延续不依赖连续在店；离店间隙不计时。
4. 日间与夜间分别累计时长并取整。跨 22:00 边界前后的零散分钟不合并取整。

其中第 2 条直接影响 05:00–16:00 等跨夜至下午的金额，第 4 条会使 21:40–22:20 的两个 20 分钟分别舍去。实施前用第 7 节具体样例核对这些解释；如与实际营业口径不一致，应修改本文件中的规则、公式及相应样例，不能额外保留一条猜测性的计费路径。

## 5. 唯一计费算法

### 5.1 时间归集

按门店时区，以“前一日 22:00 至当日 22:00”为一组计费记录，组标识取当日日期。每名会员分别累计：

| 实际时段 | 累计内容 |
|---|---|
| 前一日 22:00–当日 08:00 | 夜间实际游玩秒数 |
| 当日 08:00–12:00 | 早鸟实际游玩秒数及是否使用 |
| 当日 12:00–22:00 | 日间实际游玩秒数 |

这只是计算时的时间划分；夜间套餐通过与早鸟的合并封顶继续覆盖至 12:00，日间封顶通过符合条件的早鸟抵扣覆盖 08:00–22:00。

进出场区间统一采用 `[入场时间, 出场时间)`，在 08:00、12:00、22:00 切分。每一段实际在店时间恰好归入一个实际时段；恰好 08:00 出场不产生早鸟使用，零时长也不触发早鸟。跨多天逐组计算，午夜不重置封顶。

只累计去重且核对完成的进出场记录。不同记录相互重叠或起止时间非法时，先核对冲突，不能重复累加或静默修改时间。

### 5.2 累计后取整

设累计时长为整数秒 `s`：

```text
H(s) = s // 3600 + (1 if s % 3600 > 1800 else 0)
```

例如：30 分钟为 0 小时，30 分钟 1 秒为 1 小时；1 小时 30 分钟为 1 小时，1 小时 30 分钟 1 秒为 2 小时。实际精度以后台核实后的时间字段为准，不能补造精度。

必须先累计同一时段内的全部有效秒数，再调用 `H`；不能因消息、记录或内部切片数量不同而改变取整结果。

### 5.3 金额公式

以下公式用整数分计算，适用第 4.2 节的解释：

```text
N = min(7800, 2000 × H(夜间累计秒数))
E = 3000 if 早鸟累计秒数 > 0 else 0

P = min(7800, N + E)                # 12点前合计
C = E if P < 7800 else 0            # 可抵日间的早鸟费用

D = min(2000 × H(日间累计秒数), 7800 - C)

该组累计应付 = P + D
```

`P` 达到 7800 分时，按夜间封顶套餐结算，`C` 为 0；`P` 未达到封顶时，早鸟 3000 分可抵日间封顶。总金额由完整输入及规则唯一确定，不进行未经确认的套餐最低价选择。

该计算应实现为独立纯函数，输入已经核对的累计记录及规则，输出可解释的金额明细，不在计算过程中请求后台或发送 QQ 消息。

## 6. 重复进出与新增金额

每次离场更新相关周期内的完整记录，重新计算累计应付：

```text
本次新增应付 = 更新后的累计应付 - 此前已确认的累计应付
```

例如同一日间周期先玩 20 分钟，第一次新增 0 元；再玩 20 分钟，累计 40 分钟，第二次新增 20 元。已封顶后再次进入对应周期不重复收取封顶费用。

“此前已确认的累计应付”是本功能的应计记录，不等同于后台实际支付金额。历史记录更正可能产生应计差额，须作为明确更正处理，不自动执行扣费或退款。跨多个计费组的记录分别计算后汇总。

## 7. 金额验收样例

除特别说明外，以下均无此前消费、连续在店，金额按第 4.2 节解释推导；它们是待业务核对及实施验证的验收预期。

| 游玩记录 | 计算构成 | 应付 |
|---|---|---:|
| 07:00–13:00 | 夜间 20＋早鸟 30＋日间 20 | 70 元 |
| 05:00–16:00 | 夜间 60＋补差 18 达到夜间封顶；早鸟不抵日间，日间另封顶 78 | 156 元 |
| 06:00–16:00 | 夜间 40；早鸟 30 抵日间，12 点后再收 48 | 118 元 |
| 23:00–次日 10:00 | 夜间封顶覆盖早鸟，12 点后无时长 | 78 元 |
| 09:00–14:30 | 早鸟 30＋日间按 2 小时计 40 | 70 元 |
| 09:00–14:30:01 | 早鸟 30＋日间按 3 小时原价 60，合计封顶 | 78 元 |
| 同一日间周期两次各 20 分钟，无早鸟 | 两次合计 40 分钟，按 1 小时计 | 20 元 |
| 21:40–22:20 | 日间 20 分钟、夜间 20 分钟分别舍去 | 0 元 |

播报同时展示实际游玩时长、计费小时数、套餐归属、封顶减免和本次新增应付。多次进出时，还要区分本次时长与周期累计时长，不能把周期累计金额反复作为本次费用播报。

05:00–16:00 的播报示例：

```text
本次游玩：11小时

夜间：3小时，60元
早鸟：4小时，夜间套餐补差18元
夜间套餐合计：78元，早鸟不抵日间

日间：4小时，原价80元
日间封顶减免：2元
日间应付：78元

本次新增应付：156元
```

示例为展示口径，最终消息模板、会员脱敏方式及发送目标在接入实际播报场景时确定。

## 8. 实施阶段与验收

| 阶段 | 工作 | 主要验证 |
|---|---|---|
| 1：每店配置 | 门店配置结构、摄像头调用迁移、后台凭据配置、QQ 来源与门店选择 | 配置缺失／非法值、门店隔离、独立能力校验、现有人数统计回归 |
| 2：计费核心 | 固定规则和样例，实现独立计费纯函数、明细及累计差额计算 | 所有规则分支、取整与时段边界、跨日、多天、重复进出及封顶归属 |
| 3：真实业务链路 | 两个后台取数、真实 QQ 事件解析、记录关联与持久化、结算和播报 | 实际群消息接收、后台核对、重启恢复、重复／乱序事件、真实播报闭环 |

计费核心的正常路径与关键错误路径都应覆盖，尤其包括：

- 08:00、12:00、22:00 边界及前后最小时间单位，零时长、跨日期和多天。
- 30 分钟、30 分钟加最小时间单位，以及多个完整小时后的同类余数。
- 多次短时进出累计后取整、离店间隙排除、早鸟重复使用、已经封顶后再次进出。
- 夜间加早鸟未封顶、补差后封顶、进入早鸟前已封顶三种情况及对应的日间抵扣。
- 消息或后台记录重复不增加时长；等价切分不改变结果；实际时长分段之和等于核对后的总时长。
- 后台延迟、认证失败、记录缺失、身份不唯一、时间冲突、乱序及更正事件。
- 不同门店、会员、计费周期和规则版本的隔离。

真实验收必须从当前部署适配器实际收到指定播报 QQ 的群消息开始，使用配置账号读取两个后台，与相同口径的后台页面或导出记录逐条核对，最终在实际目标会话检查金额和明细。解析脱敏样例、mock 取数和算术校验不能替代真实闭环。

每阶段报告受影响模块的实际行覆盖率、分支覆盖率、功能链路通过／失败／未执行情况及原因。计费核心以全部规则分支覆盖为目标，覆盖率不能代替业务样例与真实数据核对。
